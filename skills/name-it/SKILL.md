# 命名助手

你的任务:给一个东西起**合适**的名字,并验证它能不能用。命名是高频小需求,但烂名字会长期折磨人(变量名、产品名都是),所以值得认真对待。

核心方法:**先定命名约束(给谁、什么语境、什么风格),再发散一批候选,再用排除法收敛,最后验证可用性。** 一次性甩一个名字是不负责任的。

## 何时用

- 代码命名:变量、函数、类、模块、仓库、包名。
- 产品/项目/功能命名。
- 品牌/公司/域名挑选(含查是否被占用)。
- 文件/文件夹命名(要统一规范)。
- 任何"叫什么好"的纠结。

## 何时别用

- 已经有名字,只是要改写/润色 → 不是命名问题。
- 要做完整品牌设计(logo/视觉/定位) → 命名只是其中一环,做完用 `brand-*` 系列深化。

## 命名的四类语境(规则完全不同)

先判断是哪类,套对应规则。**用错语境是命名翻车的头号原因**(比如给变量起个品牌名)。

### 1. 代码命名(可读性 + 一致性优先)
- **见名知义**:`getUserProfile` > `getData` > `gp`。
- **符合语言惯例**:驼峰/下划线/常量大小写按语言规范(Python 蛇形、JS 驼峰、常量全大写)。
- **避免缩写歧义**:`cnt` 是 count 还是 client?用全拼或无歧义缩写。
- **布尔用 is/has/can/should**:`isActive`、`hasPermission`。
- **别用否定双重否定**:`isNotEmpty` → `isEmpty` 取反更顺。
- **领域词统一**:同一概念全文一个词(别 user/customer/account 混用)。

### 2. 产品/项目命名(独特 + 好记 + 可注册)
- 简短(2-3 音节/字)。
- 好发音、好拼写、不容易读错。
- 有联想但不歧义(能联想到品类/调性,但不冒犯/不歧义)。
- 域名/商标/社交账号尽量可得。

### 3. 文件/文件夹命名(可排序 + 可移植)
- 一致前缀/编号:`01-intro.md`、`2026-08-report.md`。
- 全小写 + 连字符(跨平台安全):`user-profile.ts` 不用 `User Profile.ts`。
- 不含空格/特殊字符/中文(除非纯本地文档)。
- 时间用 ISO:`YYYY-MM-DD` 才能正确排序。

### 4. 创意命名(宠物/花名/小名)
- 个性优先,规则放宽。
- 仍要避开:谐音冒犯、容易起外号嘲笑、生僻到没人会念。

## 工作流

### 1. 先定约束(问不超过三个,别审讯)

- **给什么命名**?(变量/产品/域名/...)
- **语境/调性**?(严肃技术 / 活泼消费 / 内部代号...)
- **有没有硬约束**?(长度上限、必须含某词、避开某词、语言)

说不清就按最可能的来,标注"我假设了 X"。

### 2. 发散一批候选(给 6-10 个,分风格)

不要只给一个。按不同风格分组给,让用户挑方向:

```
风格 A:直白描述型
- {名 1}、{名 2}

风格 B:隐喻/意象型
- {名 3}、{名 4}

风格 C:简短抽象型(适合品牌)
- {名 5}、{名 6}
```

每个候选附**一句话**:这个名字赌的是什么、联想是什么、潜在问题。

### 3. 收敛(帮用户选,不替用户定)

点出每个候选的取舍:
- 好发音吗?会读错吗?
- 有没有不好的联想/谐音(尤其中文)?
- 够独特吗(搜一下会不会淹没)?
- 长期看会不会过时/局限?

### 4. 验证可用性(按类型)

- **变量/函数/文件**:检查项目内是否已存在同名(命名冲突)、是否符合团队规范。
- **包名/仓库**:npm/PyPI/GitHub 上搜是否被占用。
- **域名**:常用 TLD(.com/.io/.ai/.dev)查是否可注册;给出"已被占但可买/可换 TLD"的建议。
- **商标/社交**:提示用户重要命名要查商标和社交账号(不能自动查全,提醒即可)。

### 5. 给最终建议 + 备选

给 1 个首选 + 2 个备选,说清为什么首选。

## 发散技巧(卡住时)

- **组合法**:品类词 + 修饰词(DataFlow、QuickNote)。
- **意象法**:找和功能关联的物象(蝉→Cicada 代表持续发声;灯塔→Lighthouse 代表引导)。
- **造词法**:组合/变形出新词(Spotify、Instagram 式)。
- **缩写/首字母**:长名缩短但要无歧义。
- **外语/古语**:拉丁词根、其他语言里贴切的词(注意可读性)。
- **随机灵感**:用工具(`name-it` 时可让模型从不同角度各出几个)。

## 失败模式(别犯)

- ❌ **只给一个名字**:不给选择,用户没得挑。
- ❌ **不验证可用性**:起了个产品名,域名商标早被占。
- ❌ **语境错位**:给函数起品牌名,或给品牌起变量名。
- ❌ **忽略谐音/歧义**:中文尤其要注意谐音(褒义/贬义/尴尬)。
- ❌ **太难读/难拼**:追求独特导致没人会念会搜。
- ❌ **太长/缩写歧义**:变量名 30 字符,或 `mgr` `svc` 这种多义缩写。
- ❌ **替用户拍板**:给选项和取舍,让用户定。

## 输出格式

1. **命名约束**(我假设的语境和调性)。
2. **候选清单**(分风格,6-10 个,每个一句话取舍)。
3. **可用性验证结果**(按类型:冲突检查/域名/包名/商标提示)。
4. **首选 + 备选 + 理由**。

如果是代码命名(变量/函数),收敛到 2-3 个最佳,直接给最终建议,不用大段发散。
