# 慢SQL急诊室 (Slow-SQL ER)
> 把慢SQL从10秒降到50毫秒

## 🎯 一句话介绍

贴一条慢 SQL 进来,拿到的是一份能直接落地的诊断报告:问题在哪、为什么慢、加什么索引(给 DDL)、SQL 怎么重写(给改后版本)、优化前后扫描行数差多少、怎么验证。它把资深 DBA 和后端老手的排查习惯,固化成了五块可复用的工程资产——**慢查询四步法、EXPLAIN 逐字段红绿灯、索引设计决策清单、反模式扫描库、重写模式库**。不靠直觉,每一句建议都挂着一个理由和一条验证路径,比你直接让 AI"帮我优化这条 SQL"靠谱得多。

## 👤 谁该买

- **后端开发者**:写完 SQL,上线后线上慢到报警,却不知道是哪条没走索引、哪行写法拖死了查询。
- **DBA / 运维**:每天被慢查询工单淹没,想要一套标准化、可复用的排查流程,而不是每次都从零拍脑袋。
- **面试备战者**:白板手撕 SQL 优化题,需要的是一套能讲清"为什么"的方法论,而不是背几条零散答案。
- **数据分析师**:报表 / 导出类查询跑到分钟级,自己又改不动,干等结果。
- **技术负责人**:上线前想评审团队的 SQL 质量,缺一把统一、可量化的标尺。

## 📦 你会得到什么

- **SKILL.md 主文件**:7 大核心方法论 + 快速诊断决策树 + 5 步标准化工作流 + 10 条避坑边界,直接定义"一条慢 SQL 该怎么看"。
- **templates/explain-reading.md**:EXPLAIN 逐字段红绿灯判读规则——`type` / `key` / `rows` / `Extra` 看哪几项、红灯绿灯怎么分,附判断公式。
- **templates/index-design.md**:索引设计决策清单——该不该加、加在哪、加几个、加完会不会害了写入,给一棵有明确是非题的决策树。
- **templates/antipatterns.md**:12 条高频反模式 + 修复(大偏移分页、`SELECT *`、隐式类型转换致索引失效……),贴 SQL 逐条对照,命中即有对应修复。
- **templates/rewrite-patterns.md**:12 条重写模板(子查询→JOIN、大偏移→游标分页、函数包列→范围条件……),每条都是"原写法 → 改后写法 → 适用条件"三段式,可直接套。

## ✨ 核心卖点

1. **给的是可执行 DDL,不是"建议加个索引"**:索引建议直接给 `CREATE INDEX idx_xxx ON orders(user_id, created_at);`,列顺序写明理由,还评估对写入的副作用。买完就能直接拿去工单执行,不是听完还得自己想半天。
2. **EXPLAIN 逐字段红绿灯,0 基础也能读懂执行计划**:把 `type=ALL`、`Using filesort`、`rows` 这些抽象字段翻译成"红灯/绿灯",附一条判断公式。看完你就知道为什么这条 SQL 慢、慢在哪。
3. **12 条反模式 + 12 条重写模板,贴进来逐条对照**:覆盖 90% 以上常见慢 SQL(深翻页、N+1、隐式转换、`ORDER BY RAND()`……)。命中即修复,省掉你百度半天还拼凑不出结论的时间。
4. **中文 + 本土业务场景,不是英文 skill 硬翻译**:订单表、千万行、报表导出、灰度回看——贴的是中文真实业务,不是英文教程里的 `employees` 示例库。国内后端 / DBA 看着不隔。
5. **优化前后量化对比,说服评审 / 老板有底气**:报告里直接给 `type: ALL→ref`、`rows: 10,000,000→3,200` 这种对比表,再附可跑的 EXPLAIN 验证命令。优化不是"应该会快",是"扫描行数降了一个数量级"。
6. **封装方法论,所以能迁移、能复用**:不是一次性的工具脚本,是"慢查询四步法"这套思维。用几次之后,你自己排查的直觉也会变准——这是它比单点工具更值钱的地方。

## 📝 真实产出示例

贴一条常见的"函数包索引列 + 深翻页"慢 SQL,你会拿到这种报告:

```
## SQL诊断报告(以 orders 表 1000 万行为例)

### 1. 问题清单
| # | 问题 | 类型 | 严重度 | 依据 |
| 1 | 函数包索引列致索引失效 → 全表扫描 | 索引失效 | 高 | DATE(created_at) 拆散最左前缀 |
| 2 | 深翻页 LIMIT 1000000, 20 | 反模式 | 高 | 扫描 100 万行后丢弃 |
| 3 | SELECT * 回表 + 破坏覆盖索引 | 反模式 | 中 | Extra: 无 Using index |

### 2. 索引建议
- DDL: CREATE INDEX idx_uid_created ON orders(user_id, created_at);
- 理由: 等值列(user_id)在前、范围/排序列(created_at)在后,命中最左前缀 + 覆盖排序
- 副作用: 写入路径增加一次 B+树维护;与已有 idx_uid 部分冗余,可考虑替换

### 3. SQL重写(套用重写模式 2 + 4 + 8)
原SQL:
  SELECT * FROM orders
  WHERE user_id = 1024 AND DATE(created_at) = '2024-01-15'
  ORDER BY created_at LIMIT 1000000, 20;

优化SQL:
  SELECT id, amount, status, created_at FROM orders       -- 模式4: 指定列,可走覆盖索引
  WHERE user_id = 1024
    AND created_at >= '2024-01-15'                         -- 模式8: DATE()→范围条件,索引恢复可用
    AND created_at <  '2024-01-16'
  ORDER BY created_at LIMIT 20;                            -- 模式2: 连续翻页改游标
                                                           --   WHERE (user_id, created_at) < (:last_uid, :last_time)

### 4. 优化前后对比
| 指标 | 优化前 | 优化后 |
| type | ALL | ref |
| rows | 10,000,000 | 3,200 |
| Extra | Using filesort | Using index |

### 5. 验证方法
- EXPLAIN 对比命令(附)
- 计时前先 FLUSH TABLES / 重启连接池,避免 buffer pool 命中造成"假变快"
- 生产灰度后看 APM 的 p95/p99,别只看平均值
```

这就是你买完能产出的东西——具体到 DDL、改了哪几处、行数差多少,不是"建议优化一下"的空话。

## 🚀 怎么用

1. 把整个 `sql-optimizer` 文件夹放到 `~/.claude/skills/` 目录下。
2. 在 Claude Code 里输入 `/sql-optimizer`,粘贴你的 SQL(加上表结构和数据量级更准,比如 `orders 表 1000 万行`)。
3. 拿到一份上面那种结构的完整诊断报告——索引 DDL、重写 SQL、前后对比、验证方法,直接落地。
