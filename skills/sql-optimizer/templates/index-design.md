# 索引设计原则与决策清单

## 一、五大设计原则

### 原则1:最左前缀匹配
联合索引 `(a, b, c)` 的B+树按 `a → b → c` 排序。能用到索引的条件组合:

| 查询条件 | 是否用索引 | 用到几列 |
|----------|-----------|----------|
| `WHERE a=?` | ✅ | 1 |
| `WHERE a=? AND b=?` | ✅ | 2 |
| `WHERE a=? AND b=? AND c=?` | ✅ | 3(全部) |
| `WHERE b=?` | ❌ | 0(跳过了a) |
| `WHERE a=? AND c=?` | 🟡 只有a生效 | 1(c因缺b断层用不上,但MySQL 5.6+ ICP可在引擎层过滤) |

> 列顺序经验:**等值列在前、范围列在中、排序列在后**。如 `(status, created_at, id)` 配合 `WHERE status=? ORDER BY created_at`。

### 原则2:覆盖索引(免回表)
把 `SELECT` 需要的列都放进索引,走 `Using index`,跳过回表查主键的数据行。对高频点查收益巨大。

```
-- 高频查询:SELECT user_id, amount FROM orders WHERE user_id = ? AND status = 1
-- 推荐索引:把查询列也纳入
CREATE INDEX idx_uid_status_amt ON orders(user_id, status, amount);
-- 走 Using index,完全免回表
```

### 原则3:高区分度列优先
区分度 = `COUNT(DISTINCT col) / COUNT(*)`,越接近1越适合索引。

| 区分度 | 判断 | 举例 |
|--------|------|------|
| > 0.9 | ✅ 适合单独索引 | user_id、订单号 |
| 0.3 ~ 0.9 | 🟡 适合联合索引靠前 | 类型、分类 |
| < 0.1 | ❌ 单独索引无意义 | 性别、是否删除 |

> 低区分度列不是不能进索引,而是该放联合索引后面,靠前面高区分度列带它。

### 原则4:别对索引列做运算/函数/类型转换
以下写法**全部导致索引失效**(强制全表):

```sql
-- ❌ 失效写法
WHERE DATE(create_time) = '2024-01-01'      -- 函数包裹列
WHERE id + 1 = 100                           -- 列参与运算
WHERE LEFT(name, 3) = 'abc'                  -- 函数
WHERE name = 123                             -- 字符串列传数字(隐式转换)
WHERE phone = 13800000000                    -- 字符串列传数字
WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'  -- ✅ 改成范围

-- ✅ 等价正确写法
WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'
WHERE id = 99                                 -- 运算挪到右侧
WHERE name = '123'                            -- 类型对齐
```

> MySQL **8.0.13+** 的**函数索引**(表达式索引,`CREATE INDEX idx ON t ((DATE(create_time)))`)可救运算场景;**5.7 不支持函数索引**,只能用**生成列(generated column)索引**——先 `ALTER TABLE t ADD COLUMN d DATE AS (DATE(create_time)) STORED`,再在生成列上建索引,效果类似但需多一步。要权衡可维护性。

### 原则5:索引有代价,避免过度索引
- **写入变慢**:每次INSERT/UPDATE/DELETE要维护所有索引的B+树。一张表15个索引,写入肉眼可见变慢。
- **存储占用**:索引也要占磁盘,联合索引尤其大。
- **优化器选择困难**:索引太多,优化器可能选错。
- **定期清理**:用 `sys.schema_unused_indexes` 视图查长期未用的索引,定期清理。

## 二、"该不该加索引"决策清单

按顺序回答,任一否定就停下思考:

```
[1] 这个查询是高频的吗?(每天调用 > 1000 次)
    ├─ 否 → 考虑不加,或在低峰期看是否值得
    └─ 是 → 进入 [2]

[2] 加这个索引会让写入慢到不可接受吗?(看写入QPS和延迟SLA)
    ├─ 是 → 先看能否用现有索引改SQL,或上读写分离
    └─ 否 → 进入 [3]

[3] 已有索引能覆盖这个查询模式吗?(SHOW INDEX FROM tbl 检查)
    ├─ 能 → 改SQL去命中现有索引,不加新的
    └─ 不能 → 进入 [4]

[4] 这是等值查询、范围查询、还是排序列?
    ├─ 等值(高区分度) → 单列或联合索引前列 ✅ 强烈建议加
    ├─ 范围 → 联合索引中间列,配合前置等值列
    └─ 排序/分组 → 联合索引末列,争取免filesort

[5] 这个索引的列顺序符合最左前缀吗?
    ├─ 等值列在前 → ✅
    └─ 否则调整顺序

[6] 能否合并到已有联合索引,避免新增?
    ├─ 能 → 改索引定义(ALTER TABLE),而不是新加一个
    └─ 不能 → 新建,但记录理由

[7] 是否能做成覆盖索引(SELECT列不多时)?
    ├─ 是 → 把SELECT列也纳入,走 Using index
    └─ 否(列太多) → 放弃覆盖,接受回表
```

## 三、联合索引列顺序速查

| 查询模式 | 推荐顺序 | 示例 |
|----------|----------|------|
| `WHERE a=? ORDER BY b` | `(a, b)` | status过滤后按时间排序 |
| `WHERE a=? AND b=?` | 区分度高的在前 | user_id在前,tenant_id在后 |
| `WHERE a=? AND b>?` | 等值列在前,范围列在后 | `(status, created_at)` 配合 `status=1 AND created_at>...` |
| `WHERE a=? GROUP BY b` | `(a, b)` | 免临时表 |
| 多列等值,顺序无要求 | 高区分度在前 | 让索引更"瘦",减少扫描 |

## 四、索引副作用评估清单

加索引前过一遍:

- [ ] 写入QPS多少?这个索引会让写入慢多少?(经验值:每加一个索引,INSERT成本+5%~15%)
- [ ] 磁盘空间够吗?(索引大小 ≈ 列总字节数 × 行数 × 1.3)
- [ ] 大表在线变更用 `pt-online-schema-change` / `gh-ost` 了吗?(避免锁表)
- [ ] 是否和已有索引冗余?(`(a,b)` 已存在,又建`(a)`就是冗余)
- [ ] 加完跑一遍 `EXPLAIN`,确认真的被用上了
