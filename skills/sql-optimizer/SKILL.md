# SQL诊断与优化

把一条慢SQL从"跑10秒"优化到"跑50毫秒",靠的不是直觉,而是一套可重复的工程方法。这个 skill 把资深DBA和后端老手的排查习惯固化成五块可复用的资产:**慢查询排查四步法、EXPLAIN逐字段红绿灯、索引设计决策清单、反模式扫描库、重写模式库**。

输入一条SQL(加上表结构和数据量级更准),输出的是一份能直接拿去执行的诊断报告:问题在哪、为什么慢、加什么索引(给DDL)、SQL怎么重写(给改后版本)、优化前后扫描行数/访问类型差多少、怎么验证。不拍脑袋,每一句建议都挂着一个理由和一条验证路径。

适用场景:生产慢查询排查、上线前SQL评审、面试白板手撕优化题、报表/导出类查询加速、历史遗留SQL翻新。

## 核心方法论

### 1. 慢查询排查四步法:定位 → 分析 → 优化 → 验证

| 阶段 | 目标 | 主要手段 | 判断标准 |
|------|------|----------|----------|
| 定位 | 找到真正慢的那条 | 慢查询日志(`slow_query_log`)、APM(Datadog/SkyWalking)、`SHOW PROCESSLIST`、`performance_schema` | 按总耗时/调用次数/单次耗时三维度排序,先打最大的 |
| 分析 | 搞清为什么慢 | `EXPLAIN` / `EXPLAIN ANALYZE` / `SHOW WARNINGS`看优化器改写 | type是否ALL、rows是否远大于返回行、Extra有无filesort/temporary |
| 优化 | 动手改 | 加索引、改SQL、架构层(分页/缓存/预聚合/读写分离) | 改完前后扫描行数下降一个数量级以上算成功 |
| 验证 | 证明真变快了 | 前后EXPLAIN对比 + 实测计时 + 生产灰度回看 | 不仅看EXPLAIN,要看真实耗时;注意缓存污染 |

> 关键判断:**80%的慢查询根因是"没走对索引"或"走了全表扫描"**,先从索引和访问路径下手,再考虑重写,最后才上架构层改造(成本递增)。

### 2. EXPLAIN逐字段红绿灯(详见 `templates/explain-reading.md`)

重点看四类字段(其他是辅助):

- **type**(访问类型):`ALL`(全表,红灯)→ `index`(全索引扫描,黄)→ `range`(范围,可接受)→ `ref`(索引等值,绿)→ `eq_ref`(唯一索引等值,很绿)→ `const`(主键/唯一等值,最绿)。越往右越好。
- **key**(实际用到的索引):`NULL`意味着没走索引(红灯);`possible_keys`有但`key`为空,说明优化器没选上,可能是统计信息过期或写法导致失效。
- **rows**(扫描行数估算):这是成本核心。`rows`远大于实际返回行数 = 大量无效扫描,优化空间巨大。
- **Extra**(附加信息):`Using filesort`(红灯,额外排序)、`Using temporary`(红灯,临时表)、`Using index`(绿灯,覆盖索引免回表)、`Using where`(普通,可接受)。

> 判断公式:`如果 type=ALL 且 rows > 10万 且 Extra 含 filesort/temporary` → 几乎必有优化空间,优先处理。

### 3. 索引设计原则(详见 `templates/index-design.md`)

不是"加个索引"那么简单,要回答"该不该加、加在哪、加几个、加完会不会害了写入":

1. **最左前缀匹配**:联合索引`(a,b,c)`只有从`a`开始的条件才能用到;`WHERE b=?`用不上。索引列顺序由"过滤性 + 查询模式"共同决定。
2. **覆盖索引优先**:把`SELECT`需要的列都放进索引,走`Using index`免回表,对高频查询收益巨大。
3. **高区分度列优先**:区分度 = `不同值数 / 总行数`,越接近1越该建索引;性别/状态这种低区分度列单独建索引基本无用,适合放联合索引后面。
4. **别对索引列做运算/函数/隐式类型转换**:`WHERE date(create_time)='...'`、`WHERE id+1=2`、字符串列`WHERE col=123`(类型不匹配)都会让索引失效。这是最常见的"加了索引却没用上"。
5. **索引有代价,避免过度索引**:每个索引增加写入成本和存储。一张表十几个索引,写入会肉眼可见变慢。删掉长期不用的索引。

> 决策依据:详见 `templates/index-design.md` 的"该不该加索引"决策清单——给一个有明确是非题的决策树。

### 4. 反模式扫描库(详见 `templates/antipatterns.md`)

把SQL贴进来,按清单逐条对照。命中即有对应修复。**最先查语义正确性,再查性能**——LEFT JOIN 内表字段被 WHERE 过滤会退化成 INNER JOIN(取数直接错,详见 `templates/antipatterns.md` 第0条)。高频命中项:

- `LEFT JOIN` + `WHERE` 过滤内表字段(语义退化为 INNER JOIN,正确性问题,最先查)
- `SELECT *`(拖慢+破坏覆盖索引+网络/内存浪费)
- 大偏移分页 `LIMIT 1000000, 20`(扫描100万行丢掉;若 `ORDER BY` 是聚合结果,游标/延迟关联都失效,走重写模式13预聚合)
- 子查询能改JOIN的没改(尤其`IN (SELECT ...)`)
- `UNION`去重但本无重复(多用`UNION ALL`)
- `LIKE '%xxx'`(前置通配符,索引失效)
- `OR`跨列无合并索引(可改`UNION`/`IN`)
- 隐式类型转换(字符串列传了数字)
- `ORDER BY`非索引列(触发filesort)
- N+1查询(应用层循环查单条)

### 5. 重写模式库(详见 `templates/rewrite-patterns.md`)

把常见重写固化成可直接套用的模板:子查询→JOIN、大偏移分页→游标分页、`SELECT *`→指定列、循环单条→批量、`COUNT(*)`子查询→JOIN聚合、**聚合结果上的分页/排序→预聚合汇总表(模式13)**等。每条给"原写法 → 改后写法 → 适用条件"三段式。

> 模式2/3(游标分页/延迟关联)有明确的**失效边界**:`ORDER BY` 列是聚合结果(`COUNT`/`SUM` 别名)时两者都失效——聚合值无索引,游标写不出、延迟关联省不掉聚合本身。诊断时先检查 `ORDER BY` 的列是不是聚合结果,是则直接跳模式13,别硬套游标。

### 6. 优化前后对比:让优化可验证

光说"应该会快"不算数。必须给可验证的对比:

- **EXPLAIN对比**:记录前后`type`、`key`、`rows`、`Extra`,量化"扫描行数从120万降到3200"。
- **成本估算对比**:MySQL 5.6+ 可用 `EXPLAIN FORMAT=JSON` 看 `cost_info`;MySQL 8.0.16+ 还可用 `EXPLAIN ANALYZE` 看每步迭代器的实际行数与耗时(验证估算值与实际偏差极有用);PG 用 `EXPLAIN (ANALYZE, BUFFERS)` 看实际耗时和缓冲区。
- **实测计时**:同样数据下跑前后两个版本,计时;注意先清缓存(`FLUSH TABLES` / 重启连接池避免buffer pool命中)。
- **生产灰度**:优化上线后看APM的p95/p99,别只看平均值(平均会被长尾带飞,掩盖问题)。

### 7. 成本量化:给优化排序的依据

同时发现多个问题,先动哪个?用成本公式排序:

```
优化收益 ≈ (当前扫描行数 - 优化后扫描行数) × 单行处理成本 × 调用频率
```

- **扫描行数**:来自 `EXPLAIN` 的 `rows`,优化后估算值。
- **调用频率**:来自慢查询日志/APM的调用次数。高频小慢查询的累计收益常大于低频大慢查询,别只盯单次耗时。
- **单行成本**:回表/排序/临时表会放大,`Using filesort` 的行成本约是纯索引扫描的3-5倍。

> 排序后先做收益最高、改造风险最低的那一项。高风险项(大表加索引、改写改变语义)单独评估并和用户确认。

## 快速诊断决策树

拿到一条慢SQL,按这个顺序快速定位,不走弯路:

```
[1] 跑 EXPLAIN(或 EXPLAIN FORMAT=JSON)
    │
    ├─ type = ALL? ────────────────► 【缺索引 / 索引失效】
    │   └─ 查失效原因:函数包裹列?隐式类型转换?OR跨列?→ 反模式清单
    │   └─ 该加索引?→ 索引设计决策清单
    │
    ├─ Extra 含 Using filesort? ──► 【ORDER BY 列无索引】→ 加联合索引末列
    ├─ Extra 含 Using temporary? ─► 【GROUP BY/DISTINCT/UNION】→ 改写或加索引
    ├─ Extra 含 Using join buffer? ► 【JOIN字段无索引】→ 被驱动表加索引
    │
    ├─ rows >> 实际返回行? ───────► 【过滤不精准】→ 收紧WHERE / 加更精确索引
    │
    ├─ 子查询 / IN (SELECT)? ─────► 【改 JOIN 或 EXISTS】→ 重写模式1
    ├─ LIMIT 大偏移? ─────────────► 【检查 ORDER BY 列是否聚合结果】
    │   ├─ 物理列(如 id/created_at) → 游标分页 / 延迟关联 → 重写模式2/3
    │   └─ 聚合结果(如 cnt=COUNT(*)) → 模式2/3失效 → 预聚合汇总表 → 重写模式13
    ├─ SELECT *? ─────────────────► 【指定列 + 覆盖索引】→ 重写模式4
    │
    └─ 以上都不命中? ─────────────► 【架构层问题】→ 数据量级到了,考虑分表/缓存/预聚合
```

> 这个决策树覆盖90%以上的常见慢SQL。命中哪条就走对应的优化路径,避免"凭感觉乱试"。

## 工作流程

### Step 0 解析输入

> **单轮 / 多轮执行门禁(开工前先判定,消除"该停还是该干"的歧义)**
> ```
> 用户主动要求了"多轮沟通 / 你先问我"吗?
>   ├─ 否(默认) → 缺失项按经验补 + 显式标注折扣 → 走完 Step 1–5,绝不中止
>   └─ 是 → 仅当缺失项会颠覆结论时才先追问;否则仍按经验补继续
> ```
> 一句话:**默认行为是"给完整报告",不是"先问"**;中止追问是 opt-in 的多轮行为,不是默认。

从用户输入里抓全这些信息。**默认行为:缺什么就按经验补并显式标注折扣,然后继续走完 Step 1-5,不要因为缺信息而中止输出**。只有用户明确开启多轮对话、且缺失项会颠覆结论时,才先追问。

- **SQL语句**:完整SQL。如果是动态拼接的,要参数化后的真实形态。
- **表结构(DDL)**:`SHOW CREATE TABLE`的输出最准。**缺 DDL 的 fallback**:按经验预判(假设主键存在、JOIN 字段"可能未建索引"按最坏情况估),在报告里显式标注"未提供 DDL,以下数字为经验预判",并列出哪几条结论受影响(如"orders.user_id 是否已有索引")。
- **数据量级**:每张涉及表的行数 + 预计增长。`orders表1000万行`这种。决定优化收益预期。**缺量级的 fallback**:按 `_config.json` 的 `default_table_size`(没配则按百万级)假设,标注"量级假设,收益预估按数量级理解"。
- **数据库类型与版本**:MySQL 5.7/8.x、PostgreSQL、SQLite差异巨大(MySQL 8才有窗口函数、CTE;MySQL 8.0.16+ 的 `EXPLAIN ANALYZE` 能看每步实际耗时;PG 的 `EXPLAIN ANALYZE` 更细)。**缺类型的 fallback**:按 `_config.json` 的 `db_type`(默认 mysql)走,标注"按 MySQL 8.x 语法给建议"。
- **业务场景**:是高频线上查询(毫秒级要求)、还是离线报表(分钟级可接受)?这决定优化目标和可接受的改造成本。**缺场景的 fallback**:按"高频线上查询"的严格标准给,标注"若是离线报表可放宽分页/时效要求"。

> **单轮/多轮行为约定**:只贴了一条 SQL 没给背景的,**照常产出完整诊断报告**(走上面的 fallback + 折扣标注),报告末尾附一句"若提供 DDL 和数据量级,诊断准确度可显著提升,尤其影响 X、Y 两条结论"——这是告知,不是中止条件。用户主动说"我们多轮沟通/你先问我"时,才把"先问清楚"作为前置行为。

### Step 1 执行计划解读

- 如能连库(用户提供了访问方式):跑`EXPLAIN`/`EXPLAIN FORMAT=JSON`/`EXPLAIN ANALYZE`,拿真实计划。
- 不能跑:按SQL结构 + 表结构 + 量级做经验性预判,明确标注"预判,需实跑EXPLAIN确认"。
- 按红绿灯逐字段分析:`type`、`key`、`rows`、`Extra`四项必写;其余字段(`possible_keys`、`ref`、`filtered`)在相关时补。
- 逐字段解读规则详见 `templates/explain-reading.md`。
- 输出一句结论:**这条SQL的瓶颈是X**(全表扫描 / filesort / 临时表 / 索引选择错误 / N+1)。

### Step 2 反模式扫描

套用 `templates/antipatterns.md` 的清单逐条检查。**务必先查第0条(`LEFT JOIN` + `WHERE` 过滤内表 → 语义退化为 INNER JOIN),再查性能项**——语义错会让取数直接错,比慢更严重,而且 EXPLAIN 完全看不出来(执行计划可能很漂亮,但结果默默少行)。对每条命中,记录:反模式名、命中位置(SQL哪一段)、影响、修复方向。没命中的也过一遍,避免遗漏。这一步独立于索引建议——有些问题是写法问题,加索引救不了(比如`SELECT *`、N+1、LEFT JOIN 语义退化)。

### Step 3 索引建议

基于查询模式(过滤条件、JOIN键、排序/分组列)和表结构,给索引DDL:

- 给出具体`CREATE INDEX` / `ALTER TABLE ... ADD INDEX`语句,列顺序写明理由。
- 说明它命中了哪条索引设计原则(最左前缀/覆盖/区分度)。
- 评估副作用:对写入的影响、与已有索引是否冗余、是否可用复合索引替代多个单列索引。
- 决策依据详见 `templates/index-design.md`。
- 联合索引列顺序经验:**等值条件列在前,范围条件列在后,排序/分组列最后**。

### Step 4 SQL重写

给出优化版SQL,逐处标注"改了什么、为什么":

- 套用 `templates/rewrite-patterns.md` 的模式库,标明套用了哪条。
- 重写后若改变了语义(比如游标分页不能随机跳页),必须显式告知用户权衡。
- 重写和索引建议是配合关系:有时先重写让索引能用上,再加索引。

## 边界情况与避坑

1. **EXPLAIN的rows是估算值,不是精确值**:基于统计信息,可能偏差大。`ANALYZE TABLE`刷新统计信息后再看更准。判断用数量级(1万 vs 100万),别纠结个位精度。

2. **优化器有时比你聪明**:MySQL优化器会自己改写SQL(子查询→JOIN、常量折叠)。先`SHOW WARNINGS`看它真正执行的形态,避免你优化了一个被改写掉的部分。别在明显已经被优化器处理的地方白费劲。

3. **覆盖索引不是万能**:列数一多,索引膨胀,写入和维护成本上升。覆盖索引适合"高频、列少"的查询;列多时考虑部分覆盖或回表。

4. **加索引的隐藏代价**:写入路径变慢(每个索引一次B+树维护)、磁盘占用、可能影响优化器选择(索引太多,优化器选错)。生产加索引前看一眼当前索引清单(`SHOW INDEX FROM tbl`),避免重复建。

5. **大表加索引是高风险操作**:MySQL Online DDL在8.x有所改善,但亿级表加索引仍可能锁表或长时间占用资源。生产用`pt-online-schema-change`或`gh-ost`做在线变更,避开业务高峰。

6. **缓存污染让验证失真**:第一次查询慢(冷缓存),第二次快(buffer pool命中)。验证时要清缓存或对比冷启动多次平均,别被"第二次变快"骗成是优化生效。

7. **函数索引 / 生成列**:MySQL 8.0.13+ 支持函数索引(表达式索引,如 `CREATE INDEX idx ON t ((DATE(col)))`);5.7 仅支持生成列(generated column)索引——先建生成列再在其上建索引,效果类似但需多一步。对`WHERE date(create_time)=...`这种对索引列做运算的场景,函数索引比改SQL更优雅,但要权衡可维护性。

8. **不要为了优化而牺牲正确性**:有些重写(游标分页、去重逻辑变更)会改变语义。任何涉及语义变更的优化,必须向用户明确标注权衡,让用户决定接不接受。

9. **数据库差异要尊重**:MySQL的`LIMIT offset,size`、PG的`LIMIT size OFFSET offset`、SQLite的差异;`EXPLAIN`输出格式也各不相同。务必确认数据库类型再给建议,别套错方言。

10. **架构层才是某些慢查询的终局**:如果单SQL已经优化到极限(索引走对、重写到位)还是慢,问题往往不在SQL而在架构——数据量级到了要分库分表、读写分离、引入缓存或预聚合。这时别死磕SQL,把架构建议给出来。

## 配置

读取 skill 目录下 `_config.json`(用户不提供就不创建,用默认值):

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `db_type` | string | `"mysql"` | 数据库类型,影响EXPLAIN输出和索引语法。可选:`mysql` / `postgresql` / `sqlite` |
| `default_table_size` | number | 无 | 未提供数据量级时的默认假设(行数)。建议用户显式提供,更准 |
| `report_format` | string | `"markdown"` | 报告输出格式:`markdown` / `plain` |
| `include_benchmark` | boolean | `true` | 是否在报告中附上可跑的验证命令 |
| `severity_threshold` | string | `"medium"` | 只报告该级别及以上问题:`high` / `medium` / `low` |

> 配置是可选的。绝大多数场景不配也能用——直接把SQL和背景信息贴进来即可开工。
