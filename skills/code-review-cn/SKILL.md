# 中文代码审查

针对国内技术栈与业务场景的深度代码审查 skill。它不是"读一遍代码挑毛病",而是按 **四维扫描 → 严重度分级 → 误报过滤 → 修复导向** 的固定流程产出报告,目标是让每一条意见都可执行、可定级、可追溯。适用于提交前自检、PR 评审、外包验收、技术把关。

为什么不用英文通用审查:国内项目有自己的高频坑——金额用 double、时区硬编码 Asia/Shanghai、密钥写进 git、第三方接口无超时降级——这些坑需要专门的 checklist 才能系统捕捉,而不是泛泛的 "good practice"。本 skill 把这些坑固化成可复用的扫描流程。

每份报告的交付标准:**可执行**(每条带修复方向)、**可定级**(严重度有客观标准)、**可追溯**(标注位置与维度)。

## 核心方法论

审查不是主观挑刺,是按可复用的判定框架做结构化扫描。以下六条原则贯穿全流程,每条都给出"为什么这样判"的理由。

### 1. 四维扫描,逐维过 checklist,而非通读后凭印象

四个维度各自有明确边界,不混着评:

| 维度 | 核心问题 | 典型命中点 |
|------|---------|---------|
| 正确性 | 行为符合预期吗?有 bug、边界、空值、竞态吗? | 逻辑 bug、边界条件、空指针、资源泄漏、并发竞态 |
| 安全性 | 能不能被利用或越权?数据会不会泄露? | SQL/XSS/命令注入、越权(IDOR)、认证授权、敏感信息 |
| 性能 | 真实数据量下跑得动吗?有隐藏 N+1 吗?索引真的用上了吗? | N+1 查询、复杂度、内存、重复计算、大查询、`EXPLAIN` 红绿灯(type/Extra)、索引失效 |
| 可维护性 | 三个月后别人改得动吗? | 命名、重复代码、耦合、可读性、魔法数字 |

**判断理由**:通读后凭印象只能抓到"看着别扭"的问题;四维独立扫描能强制覆盖到容易被忽略的维度(比如正确性没问题但性能有 N+1)。具体检查点见 `templates/review-checklist.md`。

### 2. 严重度三档分级,定级有客观标准,反对"感觉严重"

| 级别 | 判定标准 | 修复要求 |
|------|---------|---------|
| critical | 会导致 bug / 安全漏洞 / 数据错误 / 崩溃,或违反法规(如明文存密码) | 必须修,阻塞合并,附可直接用的修复代码 |
| major | 影响质量 / 可维护性 / 潜在风险,不修迟早出事(如 N+1、缺幂等) | 应修,建议本 PR 处理 |
| minor | 风格 / 可读性 / 锦上添花(命名、魔法数字、注释) | 建议修,不阻塞 |

**定级三问(防主观)**:
1. 会不会出错 / 被利用 / 慢到爆 / 数据错?任一是 → **critical**。
2. 有没有潜在风险或明显维护负担?有 → **major**。
3. 都没有,只是不顺眼 → **minor**。

**兜底原则**:仍拿不准时**降级不升级**——把次要 critical 误判为 major,比把 major 误判为 critical 更安全(避免阻塞合并的争吵)。

判定标准与示例见 `templates/severity-rubric.md`。

**分级判定示例**(体会临界情况如何定级):

| 代码情况 | 定级 | 理由 |
|---------|-----|------|
| 金额 `double` 相乘用于结算 | critical | 精度丢失会算错钱 |
| 循环内逐条查角色(用户量未知) | major | 数据量上来才慢,当前未必爆 |
| 变量名 `a` / `tmp2` | minor | 不影响功能 |
| 按 ID 查订单未校验归属 | critical | 可被越权利用 |
| `catch(Exception e){}` 吞异常 | major | 掩盖问题,不立刻爆 |
| 注释与代码不符 | minor | 误导但不致命 |
| 密码用 MD5 存 | critical | 违反合规,可被彩虹表破解 |
| 缺 `LIMIT` 的统计查询 | major | 数据量大时拖垮 |

### 3. 中文项目常见坑专项检查(差异化核心)

通用审查抓不到、国内项目高频踩坑的六类坑,必须单独扫一遍:

| 类别 | 高频问题 | 默认严重度 |
|------|---------|-----------|
| 国际化 i18n | 时区硬编码、GBK 编码陷阱、字符串拼接不可翻译 | major |
| 支付 | 金额用 double/float、无幂等、无对账 | critical |
| 并发 | 锁粒度过大、竞态、死锁、伪单例 | critical/major |
| 配置 | 密钥硬编码、环境未隔离、默认值不安全 | critical |
| 第三方依赖 | 无超时、无降级、无限流、无重试策略 | major |
| 日志 | 密码/身份证打日志、日志级别乱用 | critical/major |

**判断理由**:这些坑在英文审查里很少被当成"必查项",但在国内电商、金融、SaaS 场景里几乎每个项目都踩过。详细清单见 `templates/cn-pitfalls.md`。

### 4. 误报过滤——先确认是约定还是 bug,再决定报不报

四类"看着像 bug 实则约定"的情况,默认不报或只记 note:

| 情况 | 为什么不报 | 处理 |
|------|-----------|------|
| 框架约定文件 | 中间件、路由注册、配置装载本来就有大量"看似重复"的代码 | 跳过 |
| 动态加载 | 反射、SPI、importlib 的字符串路径是设计而非漏洞 | 跳过 |
| 测试 mock | mock 返回固定值、绕过校验是测试需要 | 跳过 |
| 生成代码 | ORM 映射、protobuf、Swagger 生成物,改了也重生成 | 明确说明并跳过 |

同时区分 **真 bug** 与 **个人风格偏好**:命名风格、括号换行、缩进,只要项目内有统一约定(从 CLAUDE.md / .editorconfig 读到)就不报。**噪音越少,真正的 critical 才越显眼**——一份 50 条全是 major 的报告,不如一份 3 条 critical + 5 条 major 的报告有用。

**常见误报速查**(看到这些先确认再决定报不报):

| 看着像 bug | 实际多半是 | 确认方式 |
|-----------|----------|---------|
| 字符串拼接 SQL | ORM 内部实现 / 拼接的是常量 | 看变量来源是否用户输入 |
| 大段重复代码 | 框架生成的映射 / 多态未识别 | 确认是否生成物或基类 |
| 全局可变状态 | 单例配置容器(Spring 容器) | 看是否框架管理的 bean |
| 空的 catch | 有意吞掉的已知异常 | 看注释 + 异常类型 |
| 无超时的调用 | 框架已设全局默认值 | 查框架配置(如 RestTemplate / axios 实例) |
| 看似可越权的查询 | 已被中间件/拦截器统一鉴权 | 查中间件链 / 装饰器 |

### 5. 修复导向——只报问题不给方向等于没报

按严重度决定修复建议的详细程度:

- **critical** → 必须给**可直接用的修复代码片段**(完整函数或 diff),验证思路可通过。
- **major** → 给明确修复方向 + 关键代码行,不强制完整 diff。
- **minor** → 一句话指明方向即可。

修复代码必须尊重项目已有约定(有 `CLAUDE.md` 时从 Step 0 读取),**不要引入项目没用的新库**——建议用 BigDecimal 就别顺手推荐换整个货币框架。**无 `CLAUDE.md`(粘贴场景)时,按语言生态主流约定给修复代码,并在代码注释里标注"按实际 driver/项目约定调整"**——不要因为没有项目约定就让修复代码变成"需确认"占位,主流约定足以让代码可直接粘贴落地。

### 6. 报告按严重度分组、可直发 PR

报告结构固定:critical 组在前,major 次之,minor 最后;每条含位置(文件:行)、维度、问题、严重度、修复建议。开头给一段总体结论 + 必修项计数,便于快速决策是否合并。一份报告贴到 PR 评论就能用,不用二次整理。模板见 `templates/review-report.md`。

## 工作流程

### Step 0 解析输入与范围

从 `$ARGUMENTS` 提取四类信息,缺啥问啥,但不强制阻塞:

| 输入 | 含义 | 缺省处理 |
|------|------|---------|
| 代码/路径 | 待审查的文件或目录 | 要求用户提供 |
| 重点维度 | 仅审某一维(安全/性能…) | 默认四维全审 |
| 语言/栈 | Java/Go/Python/Node… | 从文件扩展名推断 |
| 审查范围 | 单个 PR、整模块、单文件 | 默认给定路径 |

同时优先读项目根的 `CLAUDE.md` / `README.md` / `.editorconfig`,提取项目约定(命名规范、框架版本、已知约束),作为 Step 4 误报过滤、Step 5 修复建议的依据。

**粘贴场景约定降级(重要)**:若用户直接粘贴代码片段而非给路径,Step 0 读不到 `CLAUDE.md` / `.editorconfig` / 依赖清单(`requirements.txt`/`go.mod`/`package.json`)。此时**不要让约定无处落地变成循环依赖**——按下述降级规则走,审查照样能产出可用结论:

| 项目约定来源 | 有路径时 | 粘贴场景(无项目文件) |
|------------|---------|--------------------|
| 命名/风格约定 | 读 CLAUDE.md / .editorconfig | **按语言生态主流约定**(PEP 8 / Google Java Style / Effective Go),不报风格类 minor |
| 框架/driver 类型 | 读依赖清单确认(如 psycopg2 vs MySQLdb) | **按该语言最主流 driver 给修复代码**(如 Python 默认 `%s` 占位符、DBAPI 风格),并在代码注释里标注"按实际 driver 调整" |
| 已知约束/豁免 | 读 CLAUDE.md 的 `## code-review` 小节 | 视为无豁免,按默认规则全审 |

粘贴场景读不到的约定**不阻塞结论**——用"主流约定 + 显式标注可调整"代替"需确认后才能写修复"。具体到修复代码:占位符语法、ORM 写法、日志格式一律走该语言生态默认值,代码块上方加一行 `# 按实际 driver/项目约定调整`,而不是在正文里散落"未提供/需确认"的叙述。读完粘贴片段后直接进 Step 1。

### Step 1 通读建立整体理解

不要上来就逐行挑刺。先花一轮建立模型:
- **架构与分层**:Controller/Service/DAO 还是其他分层?数据流怎么走?
- **入口与出口**:HTTP 入口、消息消费、定时任务分别在哪?
- **依赖**:用了哪些第三方库?版本?(扫 `pom.xml`/`go.mod`/`package.json`/`requirements.txt`)
- **数据模型**:核心实体、关键字段(尤其是金额、时间、状态机字段)。

**理由**:脱离上下文的逐行审查会误报一堆"看起来不对但其实是设计"的问题。建立理解后,Step 2 的扫描才有靶子。

### Step 2 四维逐维扫描

对每个维度**独立**过一遍 `templates/review-checklist.md`。注意是逐维,不是一遍过四维——混在一起会漏掉某维。对每个命中点记录:
- 位置(文件:行)
- 维度
- 初步严重度(此时不定稿,Step 4 校准)

### Step 3 中文项目常见坑专项检查

独立于 Step 2,过一遍 `templates/cn-pitfalls.md`。这一步的坑往往是"四维 checklist 没显式列、但国内高频"的,必须单独扫一遍。重点关注:金额类型、时区、幂等、超时、密钥、日志敏感信息。即使是只审"安全"维度的请求,支付与密钥这两类坑也值得顺带扫一下。

### Step 4 严重度分级 + 误报过滤

- 对 Step 2/3 的命中点,按 `templates/severity-rubric.md` 的"定级三问"校准严重度。
- 应用误报过滤(核心方法论 4):框架约定、动态加载、测试 mock、生成代码默认降级或不报。
- **去重**:同一根因引发的多处只报一次,其余在报告里引用位置(如"同类问题另见 OrderService.java:88、RefundService.java:120")。

### Step 5 生成修复建议

按严重度决定修复建议详细程度(核心方法论 5)。关键约束:
- critical 的修复代码要能直接替换,变量名、导入与项目一致。
- 修复方向要尊重项目已有约定,不擅自引入新依赖。
- 涉及并发的修复,先说明"为什么这样改不会引入新竞态",再给代码。

#### 规则 A:同函数多 critical 合并修复(防签名互斥)

多个 critical 命中**同一个函数**时(典型:同一个 `create_order` 同时有 SQL 注入、金额 float、缺幂等),**禁止各自给一份独立修复函数**——独立函数的签名几乎必然互斥(一个改参数名、一个加新参数、一个改返回值),开发者无法同时落地。必须按下述合并:

1. **先建索引**:扫一遍所有 critical,按"目标函数"分组。同一函数下有 ≥2 条 critical 的,标记为"合并组"。
2. **纳入同函数的 major/minor 签名冲突项**:再扫一遍 major/minor,凡**改动同一函数签名/参数/返回值**的(典型:m5"create_order 只返回 total,应返回 order_id"与统一版返回值冲突),一并并入该函数的合并组——在统一版里一并修复并标注贡献(如"m5 贡献:返回值改 lastrowid")。**判断标准**:该 major/minor 的修复若单独落地,会与统一版签名/返回值打架 → 必须并入;只是改函数体内一两行且不动签名的(如加一行日志),不必并入,正文照常单给。这一步堵住"critical 合并了、major 却另起一份冲突签名"的残留漏洞。
3. **产出唯一一份统一修复函数**:签名 = 所有修复(含 step 2 并入的 major/minor)的**并集**(新增参数取并集、参数类型按最严约束取、返回值按需合并)。这份函数只写一次。
4. **各条引用统一函数,说明本条贡献**:在每条 critical(及 step 2 并入的 major/minor)的"修复建议"里,写"采用下方「统一修复后的 create_order」"+ 用一句话点明本条往统一版里加了什么(如"C3 贡献:amount 改 int(分)、删 `*1.0`;C4 贡献:新增 idem_key 参数 + UniqueViolation 分支;m5 贡献:返回值改 lastrowid")。
5. **逐条只贴「可叠加定位片段」,禁贴函数级补丁**:合并组内每条 critical 的正文只展示本条针对的 diff 片段(1-3 行,如"第 6 行拼接 → 参数化绑定"),片段开头必须加"变化行"锚点(如 `# ↓ 第6行,仅 SQL 行变化`),**不得单独给出一份看似可直接替换的函数级补丁**(不含其他修复的"完整函数"贴片)——否则它就是与统一版互斥的第二份落地版(重跑暴露:正文 C1 给了一份无幂等的 create_order 补丁,与末节统一版互斥)。唯一直接可替换的代码只允许出现在末节「统一修复」。
6. **统一函数放在报告末尾「统一修复后的完整文件/函数」节**(见模板),作为最终落地版;正文的逐条修复仅展示该条针对的 diff 片段。
7. **自检签名一致**:统一函数的参数列表、类型、返回值必须内部自洽,且能覆盖组内每一条 critical **及 step 2 并入的 major/minor**的修复点;有冲突(如 C3 要求 amount 改 int 分、C1 的旧 total 变量已无意义)以**最严修复为准**,删掉被覆盖的旧逻辑。

> 反例(本次动态测试暴露的 bug):C1 修 SQL 注入保留 `total`、C3 把 amount 改 `Decimal` 并加 `RETURNING id`、C4 又加 `idem_key` 参数——三份 `create_order` 签名互斥,无法同时应用。合并后应只有一份:`def create_order(amount_cents: int, user_id: int, idem_key: str) -> int`,内含参数化 + 分 + 幂等三重修复。

#### 规则 B:粘贴场景修复降级(防约定循环依赖)

粘贴场景(无项目路径/CLAUDE.md/依赖清单)给修复代码时,按 Step 0 的降级表走:**走语言生态主流约定,不让"约定无处落地"卡住修复**。

- 占位符/driver 写法用该语言默认值(Python DBAPI `%s`、Java JDBC `?`、Go `database/sql` `$1`),**代码块首行加注释 `// 按实际 driver/项目约定调整`**。
- 不确定的框架细节(如 ORM 是 Django 还是 SQLAlchemy),给**纯 SQL/标准库版本**作为可落地默认,不强行猜框架。
- **禁止把"未提供/需确认"当修复内容写进正文**——主流约定已经是可落地的修复,不需要确认就能贴。需要用户拍板的(如"上层是否已有幂等")走规则 C 的 `<需确认>` 标记,不卡修复代码本身。

#### 规则 C:占位与待确认项集中化(防散落、保直发)

报告承诺"可直发 PR 评论",因此正文里的不确定项**必须集中、可扫描**,不能散落成"需确认/未提供"的叙述。规则:

1. **统一标记**:所有需要用户确认/补全的点,一律用 `<需确认: xxx>` 尖括号标记,**不要**用"需确认""未提供""待定"等自由文本散落正文。
2. **集中到顶部「待确认清单」**:报告开头(审查结论之后、Critical 之前)放一个「待确认清单」小节,逐条列出本次审查中所有 `<需确认>` 项 + 一句"确认后影响哪条结论"。正文不再重复展开叙述,只保留 `<需确认: xxx>` 内联标记。
3. **修复代码保持可直接粘贴**:critical/major 的修复代码块里**不放"未确认"叙述**,只放可执行代码。必须随 driver/约定变化的地方,用**通用占位符 + 注释**(如 `db.execute(sql, params)` 风格,注释写"按实际 driver 调整"),而不是在代码块里写"# 需确认 driver"。
4. **数量硬上限**:全报告 `<需确认>` 不超过 5 条;超过说明审查过度依赖外部信息,应回到规则 B 用主流约定兜底,把待确认项压到 5 条以内。
5. **数量自检**:对**待确认清单区**做 `grep -c '<需确认:'` 计数(只数尖括号标记,不数裸"需确认"二字——后者会把清单条目与正文内联引用重复计数,产生假超限)。结果 ≤5;若超过,回规则 B 用主流约定兜底压到 ≤5,不要带超出门。

### Step 6 输出审查报告

套用 `templates/review-report.md` 模板:按 critical/major/minor 分组,每条含位置、维度、问题、严重度、修复建议。开头给总体结论 + 必修项计数 + 合并建议(阻塞 / 条件通过 / 通过)。

**输出前自检**(避免报告失焦):
- [ ] critical 每条是否都附了可用修复代码?
- [ ] 安全类 critical 是否都给了利用路径?给不出的已降级?
- [ ] 同一根因是否已去重,只报一次?
- [ ] 误报是否已过滤(框架约定 / 生成代码 / 测试 mock)?
- [ ] minor 是否控制在合理数量,没淹没重点?
- [ ] **同函数多 critical 是否已合并**(规则 A)?全报告对同一函数不得出现 ≥2 份互斥签名的修复代码,合并组必须有唯一的「统一修复」版。**同函数改签名/返回值的 major/minor 是否已一并并入合并组**(step 2),而非另起一份冲突签名?
- [ ] **粘贴场景是否走了降级**(规则 B)?修复代码是否走主流约定、加了"按实际 driver 调整"注释,而非卡在"需确认"。
- [ ] **占位是否统一收敛**(规则 C)?自由文本"需确认/未提供/待定"叙述是否已全部改为 `<需确认: xxx>` 标记并集中到顶部「待确认清单」;正文是否还有散落的确认叙述;总数 ≤5;修复代码块内是否干净可直粘。

## 高效审查技巧与工具用法

本 skill 的 `allowed-tools` 包含只读 git 命令,善用它们能让审查事半功倍:

| 工具/命令 | 用途 | 何时用 |
|----------|------|-------|
| `git diff <branch>` | 看本次改动范围 | PR 审查首选,聚焦改动而非全量 |
| `git diff --stat` | 快速看重构规模 | 判断是否需要拆分审查 |
| `git log -p <file>` | 看文件历史改动 | 判断"这行为什么这么写",避免误报设计意图 |
| `git show <commit>` | 看单次提交 | 定位某段逻辑引入的原因 |
| `Grep` | 全局搜同类模式 | 发现一处后批量找同类(如所有 `double` 金额) |
| `Glob` | 定位约定文件 | 找 `*Middleware*`、`*Config*` 确认是否框架约定 |

**审查节奏建议**:小 diff(单文件 / 单函数)直接四维扫;中 diff(单模块)先 `git diff --stat` 看结构再扫;大 diff(跨模块)按模块拆,分多次报告,每次聚焦一个 critical 主题(如"本次只审支付链路")。**不要试图一次扫完几千行**——疲劳审查会漏掉真正的 critical。

## 边界情况与避坑

- **大型 PR / 全仓库**:不要一次性扫几千行。建议按模块或按 `git diff` 拆分,否则报告会失焦、critical 被淹没。优先审查 diff,而非全量重读。
- **不熟悉的框架**:先把框架的"约定优于配置"点查清(Django 的 ORM、Spring 的 AOP、Rails 的回调、MyBatis 的 XML 映射),否则会把约定当 bug 报。
- **业务正确性**:本 skill 能查"代码是否符合逻辑",但查不了"业务规则本身对不对"——业务规则对不对要靠需求文档和产品确认,别把业务判断外包给审查。在报告附注里点明这一点。
- **性能结论需谨慎**:不跑 benchmark 不要下"这里慢"的定论,只能说"存在 N+1 / O(n²) 的风险,数据量大时会放大"。把"风险"和"已实测慢"区分开。
- **安全结论需克制**:报"存在 SQL 注入"必须能给出构造输入的路径(用户输入 → 拼接 → 执行);只看到拼接不等于可注入(若是内部常量拼接则降级)。给不出利用路径就降级为 major 并标 `<需确认:>`,进顶部待确认清单(见规则 C)。
- **生成代码 / 第三方代码**:不在审查范围(改了也没用,要改改源或升级依赖)。明确跳过并说明,必要时建议"升级依赖版本"而非"改依赖代码"。
- **并发判断是高频事故区**:看到 synchronized / Lock / sync.Map / mutex 不要急着报"锁粒度"。先确认:临界区里做了什么?有没有替代方案(无锁结构、CAS、队列、原子操作)?误报并发问题会显得不专业。只有锁内确实做了 IO / 远程调用 / 大计算,或确实存在 check-then-act 竞态,才报 critical。
- **测试代码**:测试里的硬编码、绕过校验、mock 返回值是测试需要,不报。但测试本身覆盖率不足、断言缺失(只测不抛异常不算断言)可记 minor。
- **前端代码的特殊性**:XSS 是前端重点(`v-html` / `dangerouslySetInnerHTML` / `innerHTML`);但前端的状态管理"看着乱"多为框架范式(React hooks 依赖数组、Vue 响应式),不要按后端 OOP 标准报可维护性。CSRF token 是否随请求带上是常被漏掉的安全点。
- **数据库迁移 / SQL 变更**:DDL 是否锁表(大表加索引要走 online)、是否有回滚脚本、是否丢数据(`DROP COLUMN` 无过渡期)。这类问题影响上线,按 major 报。
- **API 契约变更**:字段重命名 / 删除 / 类型变更属于破坏性变更,即使代码逻辑没问题也要报 major(影响调用方)。新增字段、新增可选参数一般不报。

## 配置

本 skill 不要求任何专用配置文件,所有偏好均为可选。若存在以下来源,按优先级读取;**用户不提供就走默认,绝不自建配置文件**。

1. `$ARGUMENTS` 里用户直接指定(如"只审安全""只报 major 及以上")——最高优先。
2. 项目根 `CLAUDE.md` 中 `## code-review` 小节下的键值(若存在,Step 0 已读取)。
3. `.claude/settings.json` 里的 `code-review` 对象(若存在)。

可识别的可选字段:

| 字段 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `focusDimensions` | string[] | 全四维 | 限制本次只审某几维,如 `["安全"]` |
| `severityFloor` | string | `minor` | 报告下限,如 `major` 则只报 major 及以上 |
| `language` | string | 自动推断 | 强制指定语言栈 |
| `skipGenerated` | boolean | true | 是否跳过生成代码目录 |
| `customPitfalls` | string[] | [] | 项目特有的额外坑清单(追加到 cn-pitfalls 之后扫) |
| `reportFormat` | string | `markdown` | 输出格式,目前支持 markdown |

`CLAUDE.md` 写法示例:

```markdown
## code-review

- focusDimensions: ["安全", "性能"]
- severityFloor: major
- customPitfalls:
  - 内部 RPC 必须带 traceId
```

找不到任何配置来源时不报错,默默走默认。
