# 中文代码审查官 · 代码挑刺师
> 四维扫描,专挑英文 review 抓不到的中文坑

## 🎯 一句话介绍

它解决代码 review 流于主观挑刺、抓不到真问题的痛点——尤其补上英文通用 review 抓不到的中文项目高频坑:金额用 double、时区硬编码 `Asia/Shanghai`、密钥写进 git、支付无幂等。不是让 AI 通读一遍凭印象说几句,而是按**四维扫描 → 严重度分级 → 误报过滤 → 修复导向**的固定流程,产出一份可直接贴进 PR、按 critical/major/minor 分组的审查报告,封装四维 checklist、客观定级三问、国内六大类高频坑等六条核心方法论,每条 critical 都附可直接复制的修复代码。

## 👤 谁该买

- **技术 Leader / 架构师**——每天评审 N 个 PR,疲于逐条把关,想要一份有定级、有修复、能直接转发给作者的标准化报告。
- **中后端开发者(提交前自检)**——不想等 review 时被挑出低级坑,提交前自己先扫一遍,critical 修完再推。
- **外包/乙方项目验收方**——交付质量参差,需要一份结构化、可追溯的验收清单,而不是"看着还行"。
- **电商/金融/SaaS 团队**——金额算错、越权、密钥泄露、支付无幂等,这些坑出一个就是事故,需要专门 checklist 兜底。
- **带新人的团队**——把团队的 review 标准固化成 skill,新人照着四维 + 六大坑自审,统一质量基线。

## 📦 你会得到什么

- **SKILL.md 主文件**——完整的六条核心方法论 + 七步工作流程,定义"什么叫一次合格的代码审查"。
- **templates/review-checklist.md**——四维逐维扫描清单(正确性 / 安全 / 性能 / 可维护),含 MySQL `EXPLAIN` 红绿灯解读与索引失效七类排查。
- **templates/severity-rubric.md**——严重度三档判定标准 + 防主观的"定级三问" + 临界案例对照表。
- **templates/cn-pitfalls.md**——国内项目六大类高频坑清单(i18n / 支付 / 并发 / 配置密钥 / 第三方依赖 / 日志),每类附默认严重度。
- **templates/review-report.md**——报告输出模板,按 critical/major/minor 分组,开头给总体结论 + 必修项计数 + 合并建议,贴进 PR 即用。

## ✨ 核心卖点

- **专扫中文项目的高频坑,而非泛泛 best practice**——内置金额用 double、时区硬编码 `Asia/Shanghai`、密钥写进 git、支付无幂等、日志打身份证号等六类国内必踩坑。对买家的意义:市面英文审查 skill 抓不到这些,而你的项目恰恰栽在这些坑上。
- **严重度有客观标准,拒绝"感觉严重"**——critical/major/minor 三档,配"定级三问"防主观,且原则是"拿不准就降级不升级"。对买家的意义:报告不会被情绪化定级带偏,真正该阻塞合并的 critical 才会浮上来,减少与作者的争吵。
- **每条 critical 附可直接复制的修复代码**——不是只说"这里有问题",而是给到能直接替换的 diff,变量名和导入与你的项目一致。对买家的意义:作者拿到报告就能动手,不用再二次翻译,review 闭环更快。
- **先过滤误报,噪音越少越聚焦**——框架约定文件、生成代码、测试 mock、动态加载默认跳过;风格问题按项目约定不报。对买家的意义:一份 3 条 critical + 5 条 major 的报告,远比 50 条全是 major 的报告有用——critical 才显眼。
- **报告开箱即贴 PR**——固定结构按严重度分组,开头给结论 + 必修计数 + 合并建议(阻塞 / 条件通过 / 通过)。对买家的意义:不用二次整理,Claude Code 跑完直接复制进 PR 评论区。
- **内嵌 MySQL EXPLAIN 红绿灯解读**——国内绝对主流的 MySQL,给到 type 列与 Extra 列的红黄绿判读表 + 七类索引失效清单。对买家的意义:性能审查不只停在"可能有 N+1",而是能落到索引到底有没有用上。

## 📝 真实产出示例

以下是 skill 跑完后报告里 critical 条目的真实样子(摘自报告模板的真实案例):

```
## 🔴 Critical(必须修,阻塞合并)

### C1. 支付金额计算使用 double 存在精度丢失

- 位置:src/order/Price.java:42
- 维度:正确性
- 严重度:critical
- 问题:金额用 double 相乘用于结算,double 的二进制误差(0.1+0.2≠0.3)
  会导致实付金额算错,涉及钱的计算一旦上线就是资损事故。
- 修复建议(附可用代码):

  // 修复前
  double total = price * qty;

  // 修复后:金额统一用分(int)或 BigDecimal
  // 禁用 new BigDecimal(double)——它会把 double 的二进制误差原样带进来
  // 必须用 BigDecimal.valueOf(double) 走字符串中间态,
  // 或直接 new BigDecimal("0.10") 字符串构造。源头最好直接把金额存成 int(分)。
  BigDecimal total = BigDecimal.valueOf(price).multiply(BigDecimal.valueOf(qty));
```

报告开头还会给一段总览,一眼就能决策:

```
## 审查结论
- 总体结论:发现 2 个 critical(支付金额用 double、密钥硬编码),建议修复后再合并
- 问题计数:critical 2 / major 5 / minor 8
- 合并建议:🔴 阻塞
```

## 🚀 怎么用

1. 把整个 `code-review-cn` 文件夹放到 `~/.claude/skills/` 目录下。
2. 在 Claude Code 里输入 `/code-review-cn`,跟上要审的代码——给路径、给 PR,或直接粘贴代码片段均可;可指定重点维度,如 `/code-review-cn src/order/ 安全`。
3. 拿到按严重度分组的审查报告,直接复制进 PR 评论;critical 条目里的修复代码可直接替换使用。
