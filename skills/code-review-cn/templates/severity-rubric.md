# 严重度判定标准

定级必须可解释、可复核。每条报告标注严重度时,对照下表给出判定理由,不靠"感觉"。

## critical(必须修,阻塞合并)

**判定标准**:会导致 bug、安全漏洞、数据错误、崩溃,或违反法规/合规要求。不修就不能上线。

**典型示例**:
- 金额计算用 float/double 导致精度丢失(支付、对账)
- SQL 注入、XSS、命令注入等可被外部利用的漏洞(需给出利用路径)
- 越权访问(按 ID 查资源不校验归属)
- 密钥/密码硬编码进代码库
- 密码明文存储、用 MD5 存密码
- 无幂等的支付/扣款接口(可重复扣款)
- 并发竞态导致超卖、余额错乱
- 资源在异常路径泄漏(连接耗尽)
- 必检的空值未判导致 NPE/空指针崩溃

**修复要求**:必须附**可直接使用的修复代码**(完整函数或 diff)。

## major(应修,建议本 PR 处理)

**判定标准**:影响质量、可维护性或存在潜在风险。不是立刻爆炸,但不修迟早出事,或给后续维护埋雷。

**典型示例**:
- N+1 查询(当前数据量没爆,放大就慢)
- 无超时/无降级的第三方调用(依赖挂了拖垮全局)
- 时区硬编码 Asia/Shanghai(跨地区业务出错)
- 缺少必要日志(出问题没法排查)
- 大量重复代码(维护成本高)
- 函数过长、嵌套过深(改一处怕碰坏别处)
- 异常被 catch 吞掉(问题被掩盖)
- 缺少分页(数据量上来就崩)

**修复要求**:给明确修复方向 + 关键代码行,不强制完整 diff。

## minor(建议修,不阻塞)

**判定标准**:风格、可读性、锦上添花的改进。不影响功能,不修也不会出事。

**典型示例**:
- 命名不够达意(`data2`、`temp`、`doIt`)
- 魔法数字未抽常量
- 注释缺失或过时
- 括号换行、缩进等风格不一致(项目内已有约定的不报)
- 可读性优化:三元嵌套可改提前 return

**修复要求**:一句话指明方向即可。

## 定级流程(防主观)

1. 先问:**会不会出错 / 会不会被利用 / 会不会慢到爆 / 会不会数据错?** 任一是 → **critical**。
2. 再问:**有没有潜在风险或明显维护负担?** 有 → **major**。
3. 都没有,只是不顺眼 → **minor**。
4. 拿不准时,查 `cn-pitfalls.md` 里该坑的默认严重度作参考。
5. 仍拿不准,**降级不升级**——把次要 critical 误判为 major,比把 major 误判为 critical 更安全(避免阻塞合并的争吵)。
6. 安全类问题额外要求:报 critical 必须给出**利用路径**(用户输入 → 漏洞点 → 危害);给不出路径就降 major 并标 `<需确认:>`,进报告顶部待确认清单(见 SKILL.md Step 5 规则 C)。
