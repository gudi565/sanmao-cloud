# 需求转技术方案

把需求(PRD、口头描述、甚至一张草稿图)转成一份能直接进评审会的技术方案。它不是"把需求翻译成中文散文",而是用一套固定的九段式结构 + 四张可直接套用的清单模板(方案文档骨架/接口规范/WBS 拆解/风险识别),再配套技术选型决策表与评审自检清单,强制你把架构、接口、数据模型、任务、风险、排期都想到位,产出别人挑不出大毛病的设计文档与骨架代码。

> **交互模式声明(执行前必读)**:本 skill 是**多轮交互式 skill**,设计前提是 Step 1 能与需求方/PM 来回澄清。若当前是**单轮调用**(一次性 `/prd-to-tech-design` + 需求,无交互通道、无法中途等待答复),执行 Step 1 的 **fallback 分支**(见 Step 1):不暂停、改用 `[默认假设]` 标注后继续,并在方案开头醒目标注假设清单。评审前的替换确认责任在使用方,不在本 skill。

为什么这套东西值钱:写方案最容易翻车的不是"图不够好看",而是**漏想**——上线那天才发现没设计回滚、没设计幂等、慢查询没人 review、排期没算联调。这个 skill 把资深从业者脑子里的 checklist 显式化,让你每写一节都知道"这一节必须回答哪几个问题"。

适合的场景:新功能从 0 设计、老系统重构、外包报价前估排期、跨团队联调对齐、新人入职后第一次独立写方案。

## 核心方法论

这六条是贯穿全文的判断标准,不是口号。违反任何一条,方案都会在评审会被打回。

**1. 方案是写给别人看的,不是写给自己看的。** 读者(评审人、联调方、接手的人、测试)脑子里没有你的上下文。所以每一节都要回答"这一节解决读者什么疑问":背景解决"为什么要做",架构解决"整体长什么样",接口解决"我怎么对接",WBS 解决"谁什么时候做什么"。凡是不回答问题的章节,都是注水。

**2. 结构先于细节,九段式不可省略。** 技术方案不是自由发挥,它有标准结构:①背景与目标 ②整体架构 ③模块拆分 ④接口设计 ⑤数据模型 ⑥任务 WBS ⑦风险与对策 ⑧排期估算 ⑨上线与回滚。九段里漏任何一段,评审都要追问。详见 `templates/tech-design-template.md`。

**3. 接口和数据模型是契约,不是实现。** 评审阶段最该锁定的是契约:URL/方法/入参/出参/错误码/鉴权/幂等。契约一变,上下游全返工。所以接口设计必须用统一响应结构、错误码分段、分页/排序/过滤约定——详见 `templates/api-design-spec.md`。

**4. 数据模型由查询模式驱动,不是由直觉驱动。** 索引不是"给所有字段都加上",而是先列出高频查询路径,再倒推索引。主键策略、软删除、审计字段要在设计阶段就定,上线后改表代价是设计阶段的十倍。

**5. 任务拆解的粒度决定排期的准确度。** WBS 必须拆到 0.5–2 天的粒度,并标注依赖与并行关系。一个"5 天"的大任务是排不准的,五个"1 天"的小任务才排得准。详见 `templates/wbs-template.md`。

**6. 风险要套 checklist 主动识别,不要靠经验自由发挥。** 人脑记不住全部风险类别。固定套用六类 checklist:性能/安全/兼容/依赖/容量/一致性。详见 `templates/risk-checklist.md`。每类至少过一遍,有则写对策,无则标注"已评估,无"。

## 技术选型决策树

选型不是拍脑袋,是决策树。下表是选型四要素,按权重打分,而不是"我熟悉什么用什么"。评审时凡涉及"为什么选 X 不选 Y"都按此表回答。

| 维度 | 权重(%) | 关键问题 | 典型判断 | 得分(1-5) |
|------|---------|----------|----------|----------|
| 并发量 | 30 | QPS 峰值多少?读写比? | <1k QPS 用单库够了;>10k 要考虑缓存/读写分离 | [ ] |
| 一致性要求 | 30 | 强一致还是最终一致?金融? | 涉钱强一致,用事务+对账;社交流可最终一致 | [ ] |
| 团队栈 | 25 | 团队最熟什么?招人难不难? | 用团队熟悉的栈,新栈要留 20% 学习成本 buffer | [ ] |
| 成本 | 15 | 服务器/第三方/人力成本? | 云托管 vs 自建,三方 API 计费 vs 自研 | [ ] |

> 用法:对每个候选方案,逐维度打 1–5 分,乘以权重后相加。**加权合计最高者即为选型结论**。权重可按项目调整(如成本敏感型项目把"成本"调到 30),但四维度必须全填,不得留空。

### 完整打分算例(照此格式产出,不许只给表不给分)

场景:积分/流水类系统,预估峰值 3k QPS,涉钱要求强一致,团队 3 人均 Java+MySQL 背景、无人用过 TiDB,预算有限。

| 维度(权重) | A:MySQL 8.0 + Redis | B:TiDB |
|-------------|---------------------|--------|
| 并发量(30%) | 4 分:3k QPS 单库+缓存稳扛,5k 内无需分片 | 5 分:天然水平扩展,但当前规模用不满 |
| 一致性要求(30%) | 4 分:单库事务即强一致,乐观锁+对账成熟 | 5 分:分布式事务原生支持,跨片强一致 |
| 团队栈(25%) | 5 分:全员熟练,零学习成本,招人容易 | 2 分:没人用过,运维/调优都要交学费,按规则留 20% buffer 仍冒险 |
| 成本(15%) | 4 分:现有 RDS 规格即可,无新增投入 | 2 分:至少 3 节点起步,存储与实例成本约 3 倍 |
| **加权合计** | 4×0.30 + 4×0.30 + 5×0.25 + 4×0.15 = 1.20+1.20+1.25+0.60 = **4.25** | 5×0.30 + 5×0.30 + 2×0.25 + 2×0.15 = 1.50+1.50+0.50+0.30 = **3.80** |

**选型结论**:A(MySQL+Redis)4.25 > B(TiDB)3.80,选 A。写入方案时连表带算式一起贴——评审人能看到每个分数的出处,就不会追问"为什么是 MySQL"。

**触发换栈信号(写进方案,给未来的自己)**:当 QPS 持续 >10k、或单表达分库阈值且分库改造成本 > 迁移 TiDB 成本时,按同一张表重新打分复审。

### 单候选栈时怎么用:做"要不要换栈"自审

很多项目技术栈已被公司定死,只有一个候选。此时决策表不用于"A vs B 对比",而用于**自审当前栈是否扛得住**:对唯一候选逐维度打分并写明打分理由——

- 四维度均 ≥3 分 → 栈可用,直接把表贴进方案"关键架构决策"一节,作为"为什么没有选型讨论"的证据。
- 任一维度 ≤2 分 → 该维度就是**架构级风险**,必须二选一:要么在方案里给出补救设计(如"并发量 2 分" → 加分库分表/缓存方案把风险对冲掉),要么正式引入第二个候选栈重走上面对比流程。不许假装没看见——评审人一定会在这个维度上追问。

## 工作流程

按 Step 0 到 Step 8 顺序执行。每一步都有明确的"产出物",产不出来就别进下一步。

### Step 0 解析需求

读取输入(PRD 文件路径、粘贴的文本、甚至语音转写)。提取三类信息,填成一张表:

- **功能清单**:用户能做什么(动词 + 对象,如"创建订单""查询物流")。
- **非功能需求**:性能(目标 QPS/RT)、可用性(几个 9)、安全合规、容量(数据量级)。
- **约束条件**:必须用的技术栈、必须兼容的老系统、上线截止日期、预算上限。

同时用 `Read` 读取项目的 `CLAUDE.md`(技术栈约定、命名规范、已知坑)和 `_config.json`(见末尾「配置」一节)。若文件不存在,跳过并在 Step 1 提醒用户补充。

### Step 1 澄清模糊点

**不臆断**。识别需求中模糊或缺失的点,列出"需确认问题清单",每条标注影响范围。常见模糊点:

- 角色与权限边界(谁能看/谁能改)
- 数据归属与生命周期(谁的数据、保留多久、谁能删)
- 异常路径(支付失败、第三方超时、并发冲突)
- 隐含的成功指标(转化率?留存?响应时间?)

**主路径(多轮交互可用)**:把问题清单先抛给需求方/PM,**拿到答复再继续**。不要自己脑补一个答案往下写——评审会那天会被问"这个谁告诉你的"。

**fallback 分支(单轮调用,无交互通道时强制执行)**:单轮任务无法暂停等答复,此时禁止卡住、也禁止静默脑补,必须按下面四步走:

1. **先判定模式**:本次调用是否能中途等待用户回复?能 → 走主路径;不能(一次性命令、批处理、无人值守场景)→ 走本分支。
2. **逐条给默认假设**:问题清单每条增加"默认假设"一列,给出能让设计继续推进的最保守合理值,显式标注 `[默认假设]`。
3. **方案开头醒目标注**:在最终方案文档第一屏(正文任何章节之前)插入横幅:

   > ⚠️ **本方案基于 N 条未确认假设(见「需确认问题清单」),评审前必须逐条与 PM 确认或替换,否则不得进入开发。**

   N 必须等于问题清单中带 `[默认假设]` 标注的实际条数,不许写虚数。
4. **下游章节保持一致**:后续 Step 2–8 凡依赖某条假设的设计,在该处用一句话回指(如"此处按 Q3 默认假设:发放侧分摊"),让评审人能顺藤摸瓜找到源头。

**默认假设的选取原则**:选"错了也不出生产事故"的那个值(宁严勿宽)——限流阈值往严了取、有效期往短了取、金额/积分规则往保守了取。涉钱的规则(退款、过期、抵扣比例)即使给了默认假设,也必须在横幅里点名属于"必须替换"级别。

### Step 2 整体架构设计

画分层架构 + 数据流。用 ASCII 图(不依赖任何画图工具,纯文本可贴进任何文档)。至少包含:

- **分层**:接入层(网关/BFF)→ 应用层(业务服务)→ 领域层(核心逻辑)→ 基础设施层(DB/缓存/MQ/第三方)。
- **数据流**:一次典型请求从"用户点击"到"落库 + 返回"经过哪些节点。
- **关键决策**:为什么这样分层?有没有过度设计?(一句话理由即可)

架构图必须能让一个没接触过项目的人 3 分钟看懂数据走向。详见 `templates/tech-design-template.md` 第 2 章。

### Step 3 模块拆分 + 接口设计

把系统拆成职责单一的模块(每个模块一句话能讲清楚它干什么)。然后对每个模块列出核心接口,套用接口设计规范:

- RESTful 风格,资源名用名词复数
- 统一响应 `{code, message, data}`
- 错误码分段(业务码/系统码/第三方码)
- 分页、排序、过滤的统一参数
- 鉴权方式(Token/Session/签名)
- 幂等与并发(写接口必答)

详见 `templates/api-design-spec.md`。

### Step 4 数据模型设计

对每个模块给出表结构(表名、字段、类型、约束、索引),并用文字描述 ER 关系(一对多/多对多)。设计要点:

- **表名规范**:小写下划线,业务前缀(如 `order_`,`user_`)
- **主键策略**:自增 vs UUID vs 雪花,按分布式需求选
- **索引**:先列查询模式,再倒推索引(不是所有字段都加)
- **审计字段**:`created_at`/`updated_at`/`created_by`/`updated_by` 必有
- **软删除**:`deleted_at` 或 `is_deleted`,说明软删后唯一约束如何处理

### Step 5 任务 WBS 拆解

按模块拆任务,每个任务 0.5–2 天粒度,标注依赖与并行可能性。输出可直接排期的任务清单。关键规则:

- 任务名用动宾结构("实现订单创建接口"而非"订单模块")
- 每个任务标注:负责人占位、估时(人天)、前置依赖、是否可并行
- 预留联调、测试、修 bug 的 buffer(通常 = 开发估时 × 30%)

详见 `templates/wbs-template.md`。

### Step 6 风险识别

套用六类 checklist 主动识别,每类至少过一遍:

| 类别 | 核心问题 |
|------|----------|
| 性能 | 慢查询?N+1?缓存击穿?大表分页? |
| 安全 | 越权?SQL 注入?XSS?敏感数据脱敏? |
| 兼容 | 老版本客户端?数据迁移?灰度回滚? |
| 依赖 | 第三方可用性?限流?降级方案? |
| 容量 | 一年后数据量?磁盘/带宽瓶颈? |
| 一致性 | 跨库事务?消息重复消费?状态机? |

每个识别出的风险写一句对策。详见 `templates/risk-checklist.md`。

### Step 7 排期估算 + 上线/回滚方案

基于 WBS 汇总开发工时,加上联调/测试/灰度/上线窗口。并给出:

- **上线步骤**:发版顺序(先 DB 迁移还是先发代码?)、灰度策略
- **回滚方案**:代码回滚(发上一版本镜像)、数据回滚(是否需要备份、能否回滚 DDL)、配置回滚
- **核心原则**:DB 迁移必须向后兼容,代码先兼容老字段再下线

### Step 8 输出方案文档 + 骨架代码

把 Step 2–7 的产出组装成一份完整文档(套用 `templates/tech-design-template.md`),并按方案生成核心目录结构与关键接口/Model 的代码骨架(非完整实现,只到方法签名 + 一行注释)。

骨架代码的价值:让评审人一眼看到"这玩意儿真能跑起来",而不是停在 PPT 层面。骨架代码写入项目合适的目录,文件名带 `_skeleton` 后缀或放在 `docs/design/<feature>/` 下,避免污染主代码。

## 边界情况与避坑

这些是评审会上被反复追问、上线后反复翻车的点,设计阶段就要想清楚。

- **分布式事务**:跨服务写数据不要假装能用本地事务解决。明确选 saga / TCC / 本地消息表 / 对账中的一种,并说明为什么。
- **幂等**:所有写接口(尤其涉及钱、库存、状态流转)必须设计幂等键。没幂等,重试就是灾难。
- **并发**:对同一资源的并发写要回答"用什么锁"——乐观锁(版本号)/悲观锁/分布式锁。不要说"加个 synchronized"就完事。
- **分页深翻页**:`LIMIT 10000, 20` 在大表上是性能杀手,用游标分页(基于 id 或时间)替代。
- **N+1 查询**:列表接口循环里查详情是最常见翻车点,设计阶段就标注"用 join 或批量预取"。
- **时间与金额**:存数据库用 UTC + 整数分(金额),不要用浮点和本地时区。这个坑一旦上线很难修。
- **老数据兼容**:加字段要有默认值,删字段要先双写灰度,直接删 = 上线即炸。
- **第三方降级**:依赖的外部服务挂了怎么办?超时多久?重试几次?降级返回什么?不设计就等着雪崩。
- **大字段分离**:JSON/文本/二进制大字段拆到副表,避免主表膨胀拖慢所有查询。
- **缓存一致性**:先更新 DB 还是先删缓存?写多读少 vs 读多写少,策略不同。明确选一种并说明。
- **分区表必须有 MAXVALUE 兜底**:RANGE 分区只预建几个分区、不加 `PARTITION pmax VALUES LESS THAN MAXVALUE`,则最后一个分区之后的插入直接报错——等报警时已经是生产事故。兜底分区 + 每月 `REORGANIZE` 拆新分区的运维闭环必须写进方案(完整示例见 `templates/tech-design-template.md` §5.2)。
- **涉钱账户:流水恒正,退款走挂账**:流水表 `amount` 恒为正整数,方向看 `direction` 字段,禁止负流水。退款/冲正超过可用余额的部分,写账户表的挂账欠款字段(如 `arrears`),后续入账优先冲抵;同时给对账恒等式(收入−支出 = 可用+冻结+挂账)。完整流程与 DDL 见 `templates/tech-design-template.md` §5.3。

**不适用场景**:纯 UI 调整、文案修改、bugfix——这些不需要写九段式方案,直接做即可。这个 skill 适用于"有架构决策、有跨模块协作、有评审必要"的需求。

## 骨架代码示例(Step 8 产出物长这样)

骨架代码不是完整实现,而是"方法签名 + 一行注释",目的是让评审人确认目录结构和接口契约能落地。以下是一个"订单服务"的骨架样例,实际产出按项目语言调整:

```
order-service/
├── controller/
```

骨架代码的四条底线:
1. **只到方法签名**,方法体写 `// TODO: 见方案 §4` 即可,不写业务逻辑。
2. **实体类字段与数据模型表完全对应**,让人一眼对得上。
3. **接口入参/出参类必须存在**,校验注解(`@NotNull`/`@Min`)写上,契约才能锁死。
4. **第三方调用要有 Client 类**,并在注释里写"超时 Xs / 重试 N 次 / 降级返回 Y"。
5. **代码标题与类名必须一致**(写给出骨架的人):标题写"XxxServiceImpl 签名示例",代码块里就必须是 `XxxServiceImpl`,不得张冠李戴;方案正文承诺过的关键机制(如"乐观锁防超发""两阶段预扣"),骨架里必须有对应的签名兑现——标题承诺什么,代码就给什么。

> 即原"四条底线"+本条,共五条,以下统称"骨架五底线"。

**多语言目录映射**:上面的目录是 Java/Spring 风格,非 Java 项目按职责等价替换,字段与契约不变:

| 层 | Java/Spring | Go | Node.js | Python(Django/FastAPI) |
|----|-------------|----|---------|----------------------|
| 接入层 | controller | handler | routes | views / router |
| 业务层 | service / impl | usecase / service | service | service |
| 数据层 | repository | repo / store | dao / model | models / repository |
| 传输层 | dto / vo | dto / resp | dto | schema / pydantic |

无论哪种语言,骨架五底线(只到签名 / 字段对齐 / 入参出参齐全 / 第三方有 Client / 标题与类名一致且承诺的机制有签名兑现)都必须满足。

## 评审常见追问(写方案时先自答)

1. 这个接口的 QPS 预估多少?压测过吗?
2. 写操作怎么保证幂等?幂等键是什么?
3. 跨服务的数据一致性怎么保证?saga 还是 TCC?
4. 第三方挂了怎么办?超时多少?降级返回什么?
5. 这张表一年后多少行?需要分表吗?
6. 老版本客户端会报错吗?字段是只增不删吗?
7. 缓存和 DB 不一致怎么办?先更新 DB 还是先删缓存?
8. 排期里联调和测试时间够吗?关键路径是哪条?
9. 上线顺序是什么?先发 DB 还是先发代码?
10. 回滚要多久?DDL 能回滚吗?

这十条对应了前面九段式里的风险、接口、数据模型、排期、上线回滚各节。能答出来,说明方案是"想过的";答不出,说明是"写完就交差的"。
