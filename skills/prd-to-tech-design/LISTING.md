# 方案九段 · 需求转技术设计(PRD to Tech Design)
> 10 分钟出评审一次过的技术方案

## 🎯 一句话介绍

把一份 PRD(或口头需求、草稿图)在 10 分钟内转成一份能直接进评审会的完整技术设计文档。它不是"让 AI 写一篇技术散文",而是封装了一套**方案设计九段式标准结构** + **四张可直接套用的清单模板**(方案骨架 / 接口规范 / WBS 拆解 / 风险识别),再配套技术选型决策表、评审追问十条、输出自检九项,强制把架构、接口、数据模型、任务、风险、排期、回滚全部想到位——产出别人挑不出大毛病的设计文档与骨架代码。

## 👤 谁该买

- **初中级开发者**:第一次独立写方案,不知道"该写哪几节""评审会被问什么",写完心里没底。
- **技术 Leader / 架构师**:天天 review 下属的方案,痛点是"每次都要重复提醒同样的漏项",想要一套团队统一的标准。
- **外包 / 接单团队**:报价前要估排期,排不准就亏钱;想让甲方一眼觉得"这团队专业"。
- **跨团队联调负责人**:接口契约老对不齐,上下游老返工,想用统一规范锁死契约。
- **新人入职**:刚进项目就要交方案,没人带,需要一个"老员工脑子里的 checklist"。

## 📦 你会得到什么

**主文件 `SKILL.md`** —— 方案设计九段式主方法论,含六条核心判断标准、技术选型决策树、9 步工作流程、边界避坑十条、骨架代码规范、评审追问十条、输出自检九项。

**四张可独立复用的模板(`templates/` 目录):**

| 模板文件 | 一句话说清能干嘛 |
|---------|----------------|
| `tech-design-template.md` | 九段式方案文档骨架(背景/架构/模块/接口/数据模型/WBS/风险/排期/上线回滚),占位直接填,每节附"必答问题"。 |
| `api-design-spec.md` | 接口契约规范:统一响应结构、错误码分段、RESTful 约定、分页/排序/过滤、鉴权、幂等与并发。 |
| `wbs-template.md` | 任务拆解表:0.5–2 天粒度、依赖标注、关键路径、并行机会、30% 联调 buffer、估时自检。 |
| `risk-checklist.md` | 六类风险 checklist(性能/安全/兼容/依赖/容量/一致性),逐条过一遍,不再靠"经验自由发挥"。 |

## ✨ 核心卖点

1. **九段式强制结构,杜绝"漏想"才是方案翻车的真因。** 写方案最容易翻车的不是图不够好看,而是上线那天才发现没设计回滚、没设计幂等、慢查询没人 review。这套结构让你每写一节都知道"这一节必须回答哪几个问题"——对你意味着评审一次过,而不是被打回重写。

2. **中文 + 本土场景,不是英文 skill 的机翻货。** 市面上的技术设计 skill 多是英文、套国外技术栈语境。这个 skill 全程中文,错误码分段、软删除约定、灰度策略、对账方案都是国内团队真实评审会上的语言——对你意味着拿过来直接用,不用二次翻译和改造。

3. **四张独立模板 + 三张内嵌清单,买完立刻能复用。** 方案文档骨架、接口规范、WBS 拆解表、风险 checklist 四张模板都能脱离 AI,直接复制粘贴进项目文档;主文件还内嵌技术选型决策表、评审追问十条、输出自检九项三张清单。一次购买,后续每个项目都套得上——对你意味着这不是一次性消费,是团队的长期工具。

4. **评审追问十条 + 输出自检九项,把"会被问的问题"提前答掉。** 评审会上的问题大多是重复的(QPS 多少?幂等键是什么?第三方挂了怎么办?DDL 能回滚吗?)。skill 内置这十条,写方案时先自答——对你意味着评审会从"被拷问"变成"走过场"。

5. **不止出文档,还出骨架代码。** 生成核心目录结构与关键接口/Model 的代码骨架(方法签名 + 一行注释),并给出 Java/Go/Node/Python 四语言目录映射——对你意味着评审人一眼看到"这玩意儿真能跑起来",而不是停在 PPT 层面。

6. **技术选型靠决策树打分,不靠"我熟什么用什么"。** 内置选型四要素(并发量/一致性/团队栈/成本)决策表,评审时凡涉及"为什么选 X 不选 Y"都按表回答——对你意味着选型有依据,不再被质疑拍脑袋。

## 📝 真实产出示例

这是用本 skill 产出的**接口设计规范**节选(直接摘自 `templates/api-design-spec.md`),买家可直观看到"买完能产出这种东西":

```
POST /api/v1/orders
鉴权: login
幂等: 支持(Idempotency-Key)
描述: 创建订单

请求体:
  user_id     int64   必填  下单用户
  sku_id      int64   必填  商品 SKU
  quantity    int     必填  数量,>=1
  address_id  int64   必填  收货地址

响应 data:
  order_id    int64   订单 ID
  status      int     初始状态

错误码:
  30001  余额不足
  30002  库存不足
  30003  地址不存在
```

错误码分段管理(避免冲突,评审时按此对照):

| 区间 | 含义 | 示例 |
|------|------|------|
| 0 | 成功 | 0 |
| 10000-19999 | 客户端参数/业务校验错误 | 10001 参数缺失 |
| 20000-29999 | 鉴权/权限错误 | 20001 未登录 |
| 30000-39999 | 业务流程错误 | 30001 余额不足 |
| 50000-59999 | 系统/第三方错误 | 50001 DB 异常 |

> 40000-49999 段刻意预留,避免与 HTTP 4xx 状态码联想混淆。

这是 Step 8 产出的**骨架代码**样例(订单服务,实际按项目语言调整):

```
order-service/
├── controller/
│   └── OrderController.java        // @RestController,挂载 /api/v1/orders
├── service/
│   ├── OrderService.java           // 创建/查询/取消 业务编排
│   └── impl/OrderServiceImpl.java  // 方法签名 + TODO
├── repository/
│   └── OrderRepository.java        // CRUD + 自定义查询
├── model/
│   ├── entity/Order.java           // @Table("t_order") 字段映射
│   ├── dto/CreateOrderReq.java     // 入参 + 校验注解
│   └── vo/OrderVO.java             // 出参(脱敏后)
├── enums/OrderStatus.java          // 状态机枚举
└── client/
    └── InventoryClient.java        // 调库存服务,带超时与降级
```

这是 `templates/wbs-template.md` 的**任务拆解**节选,展示「0.5–2 天粒度 + 依赖标注 + 30% 联调 buffer」如何让排期排得准、关键路径找得清:

```
模块 A:订单
A-01  建表与索引              0.5d  前置:-     并行:是
A-02  实现 Model/DAO           1d   前置:A-01  并行:是
A-03  实现创建订单接口(含幂等)  1.5d 前置:A-02  并行:否
A-04  实现订单列表接口(含分页)  1d   前置:A-02  并行:是

关键路径:A-01 → A-02 → A-03 → 联调 → 测试
排期汇总:开发合计 + 联调(开发 ×30%) + 测试 + 灰度上线
```

## 🚀 怎么用

1. **放置 skill**:把 `prd-to-tech-design` 整个文件夹放到 `~/.claude/skills/` 目录下。
2. **调用**:在 Claude Code 里输入 `/prd-to-tech-design` 加上你的需求(可以是 PRD 文件路径,也可以直接粘贴一段需求描述,甚至口头描述)。
3. **拿成稿**:AI 按 Step 0–8 走完,输出一份完整的九段式方案文档 + 骨架代码,直接进评审会。
