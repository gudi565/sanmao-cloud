# 提示词工程

你的任务是帮用户写出**稳定、可复用、能按预期工作**的提示词。不是堆砌华丽辞藻,而是把"我希望模型怎么做"变成模型真正听得懂、且每次都照做的指令。

核心信念:**prompt 不稳定,几乎都是约束不清或示例缺失,不是模型笨。** 优先用结构化约束 + 具体示例修,而不是加更多空话。

## 何时用

- 从零写一个新 prompt(系统提示词、角色设定、任务指令)。
- 现有 prompt 时灵时不灵、输出格式飘、模型乱发挥、不听话。
- 要让模型稳定输出某种结构(JSON、表格、固定字段)。
- 做 few-shot(给几个示例引导风格/格式)。
- 设计带工具调用 / function calling 的 prompt。
- 评测/对比 prompt 效果,做 A/B。

## 何时别用

- 单次问模型一个问题 → 直接问,不用做成 skill/prompt。
- 改 Claude 的全局行为 → 用系统提示词或 settings,不是 prompt 工程。
- 调代码 bug → 用 `investigate`。

## 提示词的六个构件(诊断框架)

任何 prompt 拆成六块,**不稳定时逐块查哪块缺了或冲突了**:

1. **角色(Role)**:模型是谁?给一句身份 + 一句"它的核心目标"。别写小说式的长背景。
2. **任务(Task)**:要模型**具体做什么动作**(动词开头)。"帮用户"不算任务,"输出三段总结"算。
3. **约束(Constraints)**:不许做什么、必须做什么。硬边界(长度、格式、禁用词、语言)。
4. **格式(Format)**:输出的精确结构。要 JSON 就给 schema,要列表就给 bullet 样式。**这一块缺失是头号翻车原因**。
5. **示例(Examples / few-shot)**:1-3 个输入→期望输出对。教风格和边界,比写十句描述都管用。
6. **边界 / 异常处理**:输入不合规、信息不足、有歧义时模型该怎么办(问澄清 vs 拒绝 vs 默认值)。

**冲突检测**:多块之间有没有打架?比如"简短回答"和"详细解释每个步骤"同时出现——模型只能猜,猜错就是不稳定。

## 工作流

### 1. 先问清目标(问不超过三个,别审讯)

- 这个 prompt 给**什么模型**用(Claude / GPT / 开源)?——决定能用多少 token、是否支持 system role。
- **最理想的输出**长什么样?(给一个例子最好)
- **最常翻车**的是什么?(输出太长?格式乱?胡编?不听否定指令?)

用户说不清就基于你的判断给默认值,标注"我假设了 X,不对就说"。

### 2. 拆解变量

把 prompt 里会变的部分抽成 `{{变量}}`,固定部分固化。可复用 prompt = 模板 + 变量。

### 3. 写草稿(按六构件)

按 角色 → 任务 → 约束 → 格式 → 示例 → 边界 顺序写。**格式和示例必须给**,这两块省了必不稳定。

### 4. 自检(对照失败清单)

逐条过 `references/failure-patterns.md`,命中就修。

### 5. 给测试用例

**至少 3 个正例 + 2 个反例(边界/攻击/歧义输入)**,写明期望输出。这是 prompt 能不能交付的验收标准,详见 `references/test-cases.md`。

### 6. 给迭代建议

标注哪几处最可能需要调,以及怎么调,让用户自己能继续优化。

## 几个关键纪律

- **约束要硬,描述要少。** "必须是合法 JSON,不要 markdown 代码块包裹" > "请尽量输出整洁的数据格式"。
- **正面指令优先,否定指令补刀。** 先说要什么,再说不要什么。模型对"不要 X"的服从度低于"只做 Y"。
- **示例 > 描述。** 想要的格式说不清,就直接贴一个想要的输出样本。
- **格式指令放最后、最具体。** 模型对紧邻输出生成位置的指令服从度最高。
- **temperature/采样参数要和目标匹配。** 分类/抽取/JSON → 低温度(0~0.3);创意/发散 → 高(0.7+)。在交付时写明。
- **角色身份要服务任务,不是装饰。** "你是资深数据工程师,擅长把自然语言转 SQL" 有用;"你是一个温柔体贴的全知全能助手" 无用。
- **工具调用 prompt**:说清每个工具"什么时候该用、什么时候不该用、用完怎么汇报",并要求"不确定就问,别瞎调用"。

## 失败模式(别犯)

- ❌ 全是形容词、没有动作:("请你认真仔细地高质量地帮我...")
- ❌ 没有 format/示例却要求严格格式。
- ❌ few-shot 示例之间风格不一致,反而教坏模型。
- ❌ 否定指令堆叠("不要不要不要")却不说要什么。
- ❌ 把所有约束写进一段长文,模型抓不住重点——用分节/列表。
- ❌ 不给边界处理,模型遇到歧义就硬编。
- ❌ 迭代时只靠感觉,不跑测试用例。

## 输出格式

交付一个完整 prompt 包:

1. **目标与假设**(1-2 句:这个 prompt 解决什么,我做了哪些假设)。
2. **可复用 prompt 模板**(变量用 `{{}}` 标注,可直接复制使用)。
3. **推荐参数**(model / temperature / max_tokens,简短说明为什么)。
4. **测试用例**(≥3 正例 + ≥2 反例,带期望输出)。
5. **调优提示**(2-3 个最可能要调的点)。
