# 破坏性变更识别清单与迁移说明写法

> 破坏性变更(Breaking Change)是 PR review 中最高优先级的关注点。漏标一次,下游用户的系统可能在升级后静默炸雷。本清单给出五维扫描信号、命中后的双重标记规范、迁移说明的三段写法。

## 五维扫描清单

对每个逻辑变更组逐维检查,命中任一信号即判定为破坏性变更。

### 1. API 签名变更

| 命中信号 | 典型场景 |
|---|---|
| 参数增删改 | 函数 / 方法 / API 端点的入参新增(且无默认值)、删除、改名、改类型 |
| 新增可选参数 | 入参新增**且带默认值** → **不算破坏**(现有调用方零改动),不命中 |
| 返回值变更 | 返回类型收窄(`any` → `string`)、字段增删、结构改 |
| 可见性收紧 | `public` → `private`、`export` 移除、HTTP 路由从公开改为鉴权 |
| HTTP 语义 | 方法变更(`GET` → `POST`)、状态码变更(`200` → `201`)、路径变更 |
| 错误类型 | 抛出的异常类型变更、错误码重命名 |

### 2. 数据结构 / 字段变更

| 命中信号 | 典型场景 |
|---|---|
| 数据库 schema | 表/列增删改、索引变更、约束收紧 |
| JSON 字段 | 接口返回 / 配置文件的字段重命名、类型变更、必填化 |
| TypeScript 类型 | `interface` / `type` 字段收窄(可选 → 必填)、枚举值删除或改名 |
| 序列化格式 | protobuf message 字段号变更、日期格式变更(ISO → timestamp) |

### 3. 配置项变更

| 命中信号 | 典型场景 |
|---|---|
| 环境变量改名 | `OLD_NAME` → `NEW_NAME` |
| 环境变量删除 | 旧变量不再读取,且无 fallback |
| 默认值变更 | `timeout: 5000` → `timeout: 1000`(行为变) |
| 配置 schema | `.env.example`、`config.yaml` 结构变更 |

### 4. 依赖大版本变更

| 命中信号 | 典型场景 |
|---|---|
| 主版本号变更 | `react@17` → `react@18`、`express@4` → `express@5` |
| 依赖删除 | 移除某依赖且其 API 被代码直接使用(需替换) |
| 语言/运行时 | Node 18 → Node 20、Python 3.10 → 3.12 |

### 5. 行为语义变更(仅限外部可观察契约)

> **本维有范围限定**:只扫描**外部可观察契约**的变更——公开接口、公开配置、公开数据格式的同输入不同输出。**纯内部 bug 修复不命中本维**,判定纪律见下一节,不读不要定性。

| 命中信号 | 典型场景 |
|---|---|
| 同输入不同输出 | **公开接口**的默认值改、对外排序规则改、单位改(秒 → 毫秒) |
| 鉴权 / 权限 | **同一公开接口**的鉴权策略变严或变松 |
| 副作用 | 原本无副作用的**公开**操作开始写日志/发事件/改数据库 |
| 错误处理 | **公开接口**原本吞掉的错误改为抛出,或反之 |

**带默认值的改动不算破坏(重要)**:新增**可选参数(带默认值)**、新增**可选字段**、新增**带默认值的配置项**——现有调用方无需任何改动,一律不判破坏(无论落在哪一维)。反例:新增**无默认值的必填参数** → 调用方不传即炸 → 破坏。

### 判定纪律:bug 修复不自动升级为破坏性变更

第 5 维只覆盖**外部可观察契约**的变更。"修复了一个 bug"本身不在此列——老行为是错的,改对不算破坏。三步判定:

1. **改动是否落在公开契约上?** 内部函数、私有方法、未导出逻辑 → 不标破坏,结束。
2. **老行为是否是文档化 / 被合理依赖的契约?** 老行为本身是 bug(边界漏判、条件写反)→ 属 bug 修复,不标 `BREAKING CHANGE`;老行为是文档承诺或默认值的刻意变更(如公开接口分页默认 100 → 50)→ 按破坏处理。
3. **拿不准一律升级**:标破坏性变更并在迁移说明写明"可能属 bug 修复,请 reviewer 确认"——宁多标不漏标。

**方向证据义务**:任何"行为收紧 / 鉴权变严"的定性,必须在 PR 区块贴出**真实改动前后条件**(代码或 diff 片段),并推导新旧行为,让 reviewer 能亲自验证方向——方向经常与直觉相反,不允许只写结论。示例:`used < expiry` → `used <= expiry`,在 `if (used < expiry) valid` 的读法下是**放宽**(边界由过期改有效);在"used 为已用时长"的读法下才是收紧。

**bug 修复引起的行为变化仍需透明**:即使不标 `BREAKING CHANGE`,也必须在 PR 的"⚠️ 破坏性变更"区块保留一行注明"行为有变化但属 bug 修复,未标破坏"(附前后行为对比),让 reviewer 确认此判断已被考虑,而不是被漏扫。

## 命中后的双重标记

破坏性变更必须**两处同时标记**,缺一不可:

### 处 1:commit footer

```
feat(api): 用户接口字段从 snake_case 改为 camelCase

<body...>

BREAKING CHANGE: UserResponse.name_first → firstName,
avatar_url → avatarUrl。前端需同步改造。
```

关键字 `BREAKING CHANGE` 必须全大写、后接冒号与空格。semantic-release、release-please 等工具靠这个关键字触发 major 版本号。

> **替代写法**:Conventional Commits 1.0+ 也支持在提交头用 `!` 简写标记破坏性变更,如 `feat(api)!:` 或 `feat!:`,与 footer 的 `BREAKING CHANGE:` 等价。两种**二选一**,不要同时用(详见 `conventional-commits.md` 的"`!` 简写"小节)。`!` 简写适合短说明场景,仍建议在 body 中补迁移细节。

### 处 2:PR 描述顶部区块

```markdown
## ⚠️ 破坏性变更

**本 PR 包含破坏性变更**。

| 维度 | 老用法 | 新用法 | 迁移说明 |
|---|---|---|---|
| API 字段 | `name_first` | `firstName` | 过渡期 7 天同时返回两套字段 |
| 配置项 | `AUTH_JWT_SECRET` | `AUTH_SESSION_SECRET` | 启动时读老变量并打 deprecation 日志 |
```

PR 描述区块是给人看的,要用表格直观对比;commit footer 是给机器看的,要用关键字触发发版。

## 迁移说明的三段写法

每一条破坏性变更都要写清楚:**老用法 → 新用法 → 过渡策略**。

- **老用法**:具体到代码片段或配置项,不要泛指"原接口"。
- **新用法**:同样具体,最好能直接复制。
- **过渡策略**:回答三个问题——

  1. 是否提供兼容期?(几天 / 几周 / 几个版本)
  2. 兼容期内老用法是否仍可用?(双写 / fallback / deprecation 警告)
  3. 何时移除老用法?(具体版本号或日期)

### 模板

```
**老用法**(版本 ≤ vX.Y.Z):

    GET /api/user → { "name_first": "...", "avatar_url": "..." }

**新用法**(版本 ≥ vA.B.C):

    GET /api/user → { "firstName": "...", "avatarUrl": "..." }

**过渡策略**:

- 兼容期:7 天(2026-08-06 起)
- 兼容期内:接口同时返回 snake_case 与 camelCase 两套字段
- 老字段在响应中带 `__deprecated: true` 标记
- 移除时间:v2.0.0(预计 2026-09-30)
```

## 常见翻车点

1. **"我以为不算破坏"**:把可选参数改成必填,很多人觉得无害,但调用方没传就会炸。**规则:任何收紧约束的改动都算破坏**。
2. **"凡签名变了就标破坏"**:与上一条相反的翻车——新增**带默认值的可选参数**,现有调用方零改动,不算破坏。**规则:判定依据是"现有调用方是否需要改动",不是"签名文本是否变化"**。
3. **只改了类型没改逻辑**:TypeScript 把 `string | undefined` 改成 `string`,运行时无变化,但调用方代码会类型报错。**规则:类型收窄也算破坏**。
4. **改了默认值**:把分页 `limit` 默认从 100 改成 50,调用方没显式传就会拿到不同结果。**规则:默认值变更算破坏**。
5. **删了 deprecation 日志**:旧变量原本打 warning,清理时直接删,导致用户升级后静默失败。**规则:删除兼容层前先确认 deprecation 期已过**。
6. **依赖 minor 升级**:虽然是 minor,但新版本修了"看上去无害但被依赖的 bug",可能改变调用方依赖的行为。**规则:依赖升级一律在 PR 描述中注明,minor 若有行为变更按破坏处理**。
7. **把 bug 修复一律标成破坏**:任何 fix 都改变行为(从错的改成对的),按"同输入不同输出"字面执行会把所有 fix 标成 `BREAKING CHANGE`,荒谬。**规则:内部 bug 修复不命中第 5 维,按第 5 维"判定纪律"三步走;拿不准才升级**。
8. **收紧 / 放宽方向判反**:如 `used < expiry` 改 `<=`,在 `if (used < expiry) valid` 读法下是放宽而非收紧。**规则:凡定性"收紧 / 变严",必须贴改动前后真实条件与新旧行为推导(见第 5 维"方向证据义务"),让 reviewer 可验证**。

## 自检:破坏性变更是否标全?

- [ ] commit footer 是否有 `BREAKING CHANGE:`(全大写)?
- [ ] PR 描述顶部是否有 ⚠️ 区块?
- [ ] 每条变更是否写了"老用法 → 新用法 → 过渡策略"?
- [ ] 过渡策略是否回答了三个问题(兼容期 / 兼容期行为 / 移除时间)?
- [ ] 行为语义(第 5 维)命中项是否过了"判定纪律"三步(公开契约?老行为是契约还是 bug?拿不准已升级)?
- [ ] 凡定性"收紧 / 变严 / 变松",是否贴了改动前后真实条件供 reviewer 验证方向?
- [ ] bug 修复引起的行为变化,虽未标破坏,是否在 ⚠️ 区块保留说明行(前后行为对比)?
- [ ] 是否在相关 issue / changelog 中同步标注?
